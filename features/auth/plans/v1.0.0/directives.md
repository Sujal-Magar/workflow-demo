## Developer-approved decisions (apply exactly; record the ★ ones in the plan Decision Log as new D-22.. entries)

### B-1 — Service owns workflows; repositories are single-table (★)
Adopt option (a). Introduce a **transaction-runner port** (e.g. `UnitOfWork` / `TransactionRunner`) that the *service* calls to define the transactional boundary. better-sqlite3 transactions are synchronous: no `await` inside the boundary, so hashing (argon2) happens BEFORE entering it.
Repositories expose only single-table, intention-revealing operations with NO business rules, e.g.:
- `RefreshTokenRepository`: `createRefreshToken`, `revokeActiveRefreshToken({ tokenHash, now })` -> boolean (true iff an active, unexpired row was revoked), `revokeAllRefreshTokensForUser({ userId, now })`, `revokeRefreshTokenByHash`.
- `PasswordResetTokenRepository`: `createResetToken`, `invalidateUnusedResetTokensForUser({ userId, now })`, `consumeResetToken({ tokenHash, now })` -> `{ userId } | null` (conditional `used_at IS NULL AND expires_at > now`).
- `UserRepository`: adds `updatePasswordHash({ userId, passwordHash, now })`.
The **services** own the rules and sequences: rotation (revoke presented token; only if it returned true, create replacement, all in one boundary), reset (consume token; if null -> `InvalidResetTokenError`; else update password hash; revoke all the user's refresh tokens; one boundary), reset-token replacement (invalidate earlier unused + create new, one boundary). The port hands the service repository instances bound to the transaction handle. Plan §1.3 compliance claim must remain accurate. Update D-17, §5.2 layout, §5.3 BE-06/BE-07/BE-09/BE-11, §5.5, §5.6, and testing items (rollback/atomicity tests at service level with the real in-memory DB; race test for two concurrent rotations still required).

### B-2 — Frontend builds from the committed contracts package (★)
Adopt option (a). Written sequencing dependency: **BE-01 (contracts package) is the first Backend Build task and is committed before the Frontend session starts**; after that commit the Backend session continues BE-02..BE-13 in parallel with the Frontend session. This is a deliberate, documented deviation from "fully parallel" Phase 5, recorded as a ★ decision.
Consequences to apply everywhere:
- The frontend consumes `@expense-tracker/contracts` (already a workspace dependency of `frontend/package.json`; read-only: the Frontend session never edits `packages/contracts`). No provisional local types, no local schemas, no duplicated FDS message strings.
- `lib/auth/api-client.ts` builds the ts-rest React Query client from the shared contract from FE-09 onward. During the Frontend session the network is stubbed by stubbing global `fetch` (FE-12 fixtures are typed FROM the contract types and validated by the contract response schemas), not by a parallel client.
- FE-12 becomes "typed fetch-stub fixtures + helper" and gains a note that success/error bodies are typed via contract-inferred types.
- INT-01 shrinks accordingly: no schema/type swap; it removes the fetch-stub harness from production paths, relocates fixtures to `frontend/src/test/`, and confirms no message strings exist in the frontend. INT-02.. unchanged.
- Update §1.3 (drop the "temporary build-time mocks" exception), §4 execution order, §5.3 build order note, §6.1, §6.3.1 last bullet, §7 INT-01, §9 boundaries table + closing paragraph, §10 risks.

## Advisory decisions to fold in (not blocking, but applied in this pass)

1. **Composed service methods (D-18):** `AuthService.register / login / loginWithGoogle` each return the complete session result (user, access token, expiresIn, raw refresh token) by calling `SessionService.issueSession` internally. Each router handler calls exactly one service method. Rewrite D-18 to state the composed option as decided; BE-12 wording consistent.
2. **CORS methods (BE-04):** keep the existing allowed methods `GET, POST, PATCH, DELETE, OPTIONS` (do not narrow). Contract §6 keeps saying the list "includes" what auth needs.
3. **Database path base (BE-02, INT-04) (★):** a relative `DATABASE_PATH` (default `./data/app.db`) is resolved against the **repository root** (the nearest ancestor directory containing `pnpm-workspace.yaml`, found by walking up from `process.cwd()`), so the file is `<repo>/data/app.db` per `rules/architecture.md` regardless of whether the process runs from `backend/` (pnpm dev, Playwright webServer) or elsewhere. Absolute paths are used as-is; `:memory:` is passed through. Parent directory is created. `*.db` is already git-ignored.
4. **Non-object JSON bodies (contract §1, R3; BE-03; TU-13/TU-21):** distinguish (i) *missing or empty body* on an operation that requires one: treated as an empty object, every required field reports its "is required" message (unchanged); (ii) *a body that is present but valid JSON of a non-object type* (array, string, number, boolean, `null`): `400 VALIDATION_ERROR` with empty `fieldErrors`, exactly like unparseable JSON. Amend contract §1 "Absent required body" row and R3 and §5 error row; BE-03 adds a small body-shape guard after `express.json()`; add test cases.
5. **Google edge cases:** the verifier adapter treats a payload lacking `sub` or `email` as a verification failure (`InvalidGoogleTokenError`); a `GoogleLogin.onSuccess` with an undefined/empty `credential` is treated as dismissal (no request, no toast). Add to BE-08/§5.6 and §6.7 and tests.
6. **Google-unavailable flag sharing (§6.7 vs §6.2):** mount `GoogleOAuthProvider` NOT in the global `providers.tsx` but in a `GoogleAuthProvider` component (new file `components/auth/google-auth-provider.tsx`) rendered by the `/auth` page content only (so Google's script is not loaded on `/dashboard` or `/reset-password`). It exposes a small React context (`useGoogleAvailability(): { available: boolean }`) that carries client-id-configured and script-load-error state to `GoogleSignInButton`. Update §6.2 layout (providers line loses GoogleOAuthProvider), §6.7, FE tasks.
7. **Clock injection:** `JoseAccessTokenSigner` receives the `Clock` and issues/verifies against it (e.g. jose `currentDate` option on verify; `iat`/`exp` computed from `clock.now()`), so TU-08/09/18 control expiry by clock. State in BE-08 and BE-06.
8. **Refresh 401 clears cookie (BE-12):** mechanism = the `refreshSession` handler alone wraps its single service call in a local `try/catch` for `UnauthenticatedError`, and returns the shared 401 body together with the clearing `Set-Cookie`; every other error still flows to the global `error-mapper`. State in BE-12.
9. **Protected routes:** state explicitly in §6.10 that `/transactions`, `/budget`, `/goals`, `/reports`, `/profile` pages do not exist in this feature, so the guard wraps them by construction of the `(protected)` group only; an unauthenticated visit today is a Next 404, and only `/dashboard` is verifiable (TE-10) until later features add pages.
10. **Test gaps:** add (a) a component test for the D-6 stacked mobile layout (viewport below `md`: view swap, no slide transition classes); (b) a TC case for a whitespace-only name (D-8) on the sign-up form; (c) a backend API/unit test asserting raw refresh tokens, raw reset tokens and passwords never appear in server logs (except the deliberate ConsoleMailer reset URL) and that error bodies never echo them.
11. **Traceability:** BE-03 cites FDS §6 + D-17; BE-13 cites FDS §3, §6 + D-17.
12. **Ports:** keep the ports; in §10 add a confirm-at-gate item asking the developer to confirm the `PasswordHasher`, `AccessTokenSigner` and new transaction-runner ports are wanted vs `conventions.md` "avoid unnecessary abstractions".
13. **Blank flash on mode switch (§6.4):** keep unmount-on-switch; add a note in §6.4 that a brief cross-fade of the outgoing form is a Phase 6 UI-review refinement candidate (no spec change).
14. **FDS-level observations:** add to §10 a short "Accepted-risk confirmations at the gate" item: (i) Google identity is linked to an existing email/password account whose email was never verified (FDS REQ-AUTH-03 step 2; no email verification exists; external email is forbidden by tech-stack); (ii) `409 EMAIL_ALREADY_EXISTS` on registration reveals that an email is registered (FDS-mandated).
