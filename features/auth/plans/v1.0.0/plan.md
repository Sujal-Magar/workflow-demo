## 1. Scope and Decisions

### 1.1 Scope

Delivered by this feature: sign up, sign in, Google SSO, password visibility toggle, forgot/reset password (console-mailer delivery), session lifecycle (restore, renew, logout), client route guard with a placeholder `/dashboard`, and the `requireAuth` middleware that all other features depend on. Out of scope: profile creation (owned by `profile`), a production mailer, rate limiting or lockout, cleanup of expired token rows, the real dashboard and app shell.

### 1.3 Rule compliance summary

- Layering: Presentation, Service, Repository, Database only. Services never see `req`/`res` and own every business rule and multi-step sequence; repositories are single-table with no business rules; services define transactional boundaries through the `TransactionRunner` port (D-22). Drizzle is imported only by the `db/` plumbing (client, migrate, schema, `drizzle.config.ts`), the repositories and the Drizzle `TransactionRunner` implementation (`auth/repositories/`), and only repositories and that runner run queries; nothing in services or presentation imports Drizzle; `argon2`, `jose` and `google-auth-library` live only in `infrastructure/` adapters behind ports. Router handlers call exactly one service method (D-18).
- Contracts: all routes, schemas and inferred types originate in `packages/contracts`; the frontend consumes the committed `@expense-tracker/contracts` package read-only and defines no duplicate API types, schemas or message strings at any point (BE-01 is committed before the Frontend session starts, D-23).
- Libraries: only those approved in FDS section 2 (`argon2`, `jose@^5`, `google-auth-library`, `cookie-parser`, `@types/cookie-parser`, `@react-oauth/google`). No HTTP test client.
- No `any`; strict typing; named constants for magic values; kebab-case files; PascalCase components.

## 4. Execution Order

1. **P0** (orchestrator, single writer).
2. **Phase 5, sequenced start then parallel (D-23).**
   1. **BE-01 first**: the Backend session implements and commits the contracts package (`packages/contracts`) before anything else. The Frontend session does not start until that commit exists.

The Frontend session consumes `@expense-tracker/contracts` read-only and, with no backend available, stubs the network by replacing global `fetch` (FE-12). If the committed contract lacks an export the frontend needs, the Frontend session stops and reports it; it never defines a local substitute.
      This is a deliberate, documented deviation from fully parallel Phase 5, and from `.ai/prompts/build-mode.md` `Phase = Both` used as one unchanged fan-out (there the Frontend subagent builds on mock data): the orchestrator runs BE-01 first, commits, then launches the Frontend session and the rest of Backend in parallel. ### 5.4 Data model (Drizzle / SQLite)

Table names snake_case plural; IDs are UUID v4 text generated from an injectable generator; timestamps are ISO-8601 text from the `Clock`.

| Table                   | Columns and constraints                                                                                                                                                                                                                                                               |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `users`                 | `id` PK; `name` NOT NULL; `email` NOT NULL UNIQUE (lowercase); `password_hash` NULL; `provider` NOT NULL, one of `email` or `google`; `google_id` NULL UNIQUE; `created_at`, `updated_at` NOT NULL. `CHECK (password_hash IS NOT NULL OR google_id IS NOT NULL)` as defence in depth. |
| `refresh_tokens`        | `id` PK; `user_id` NOT NULL FK to `users.id` (indexed); `token_hash` NOT NULL UNIQUE (SHA-256 hex); `expires_at` NOT NULL; `revoked_at` NULL; `created_at` NOT NULL.                                                                                                                  |
| `password_reset_tokens` | `id` PK; `user_id` NOT NULL FK (indexed); `token_hash` NOT NULL UNIQUE; `expires_at` NOT NULL; `used_at` NULL; `created_at` NOT NULL.                                                                                                                                                 |

Raw refresh and reset tokens never appear in the database, logs (except the deliberate `ConsoleMailer` reset URL) or error messages. Both are 32 bytes from `node:crypto` `randomBytes`, base64url; only the SHA-256 hash is stored.

Transactions: better-sqlite3 transactions are synchronous. A `TransactionRunner` boundary callback must not `await`; anything slow or async (argon2 hashing, token generation, JWT signing, mailer) happens before or after it. A thrown error inside the callback rolls the whole boundary back.

### 5.5 Repository methods and transaction runner

Every repository method reads or writes exactly one table and encodes no workflow or business rule. Where a service needs several writes to succeed or fail together, it calls the `TransactionRunner` port and sequences the single-table methods itself (D-22).

| Repository                     | Methods                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| :----------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `UserRepository`               | `createUser({ id, name, email, passwordHash, provider, googleId, now })` (a unique violation on `email` or `google_id` surfaces as a typed persistence signal naming the column, not a raw driver error); `findUserByEmail(email)` (caller passes normalized lowercase); `findUserByGoogleId(googleId)`; `findUserById(id)`; `linkGoogleIdentity({ userId, googleId, now })` (sets only `google_id` and `updated_at`); `updatePasswordHash({ userId, passwordHash, now })` (sets only `password_hash` and `updated_at`; `provider` and `google_id` untouched).                                                                                                                                                                                                                                                   |
| `RefreshTokenRepository`       | `createRefreshToken({ id, userId, tokenHash, expiresAt, now })`; `findRefreshTokenByHash(tokenHash)` (returns the row including `userId`, or `null`; applies no rule about acceptability); `revokeActiveRefreshToken({ tokenHash, now })` (one conditional UPDATE, `token_hash = ? AND revoked_at IS NULL AND expires_at > now`; returns `true` if and only if an active, unexpired row was revoked, which is the race guard: two concurrent revocations of one token cannot both return `true`); `revokeRefreshTokenByHash({ tokenHash, now })` (no-op when absent or already revoked; used by logout); `revokeAllRefreshTokensForUser({ userId, now })` (sets `revoked_at = now` on all of that user's tokens where `revoked_at IS NULL`).                                                                     |
| `PasswordResetTokenRepository` | `createResetToken({ id, userId, tokenHash, expiresAt, now })`; `invalidateUnusedResetTokensForUser({ userId, now })` (sets `used_at = now` on every unused token of the user); `consumeResetToken({ tokenHash, now })` (one conditional UPDATE, `used_at IS NULL AND expires_at > now`; returns `{ userId }` when a row was consumed, `null` when the token is unknown, expired or used, with nothing changed; a concurrent second use cannot succeed).                                                                                                                                                                                                                                                                                                                                                          |
| `TransactionRunner` (port)     | `runInTransaction(work)`: opens a database transaction, calls `work` synchronously with repositories bound to the transaction handle (`{ users, refreshTokens, passwordResetTokens }`), commits when `work` returns, rolls back everything when it throws, returns what `work` returned. `work` is typed as synchronous (its type does not allow a promise), and at runtime `runInTransaction` throws a typed programming error (`TransactionCallbackAsyncError`) if the callback returns a thenable, rolling the transaction back. The Drizzle implementation (`auth/repositories/drizzle-transaction-runner.ts`) runs no queries itself; it only opens the transaction and builds the transaction-bound repository instances. Services define what runs together; the runner and repositories only execute it. |

### 5.6 Service behavior

Services take plain arguments, throw typed domain errors, and receive collaborators by constructor injection (repositories, ports including `TransactionRunner`, `Clock`, id and token generators, `frontendOrigin`). Services own every rule and every multi-step sequence; the repositories they call are single-table (5.5). Accepted limitation: work that happens after a boundary commits (signing the access token, `SessionService.issueSession` after `register` creates the user, the mailer call) is not inside the transaction boundary because signing is async and the boundary must be synchronous; if it fails, the response is a 500, the committed data stays (for example a rotated refresh token is lost so the user signs in again, a created account stays usable through login), and nothing is left half-applied inside a boundary.

| Domain error              | `code`                 | Mapped to |
| :------------------------ | :--------------------- | :-------- |
| `EmailAlreadyExistsError` | `EMAIL_ALREADY_EXISTS` | 409       |
| `InvalidCredentialsError` | `INVALID_CREDENTIALS`  | 401       |
| `InvalidGoogleTokenError` | `INVALID_GOOGLE_TOKEN` | 401       |
| `UnauthenticatedError`    | `UNAUTHENTICATED`      | 401       |
| `InvalidResetTokenError`  | `INVALID_RESET_TOKEN`  | 400       |

`VALIDATION_ERROR` comes from Presentation validation before services run.

- **`SessionService`**
  - `issueSession(userId)`: access token (`sub = userId`, 15 minutes, `expiresIn = 900`, signed through `AccessTokenSigner`, which issues and verifies against the injected `Clock`) and a new refresh token (256-bit, only its hash stored, `expiresAt = now + 7 days`); returns the raw refresh token to its caller (`AuthService` or the rotation path, and through it the router).
  - `rotateSession(rawRefreshToken | undefined)`: absent means `UnauthenticatedError`. Hash the token (SHA-256) and generate the replacement token and id before the boundary. Then, in one `TransactionRunner` boundary (service-owned, no `await`): (1) `findRefreshTokenByHash`, none means `UnauthenticatedError`; (2) `revokeActiveRefreshToken`, `false` (revoked, expired, or lost a race to a concurrent rotation) means `UnauthenticatedError`; (3) `findUserById`, missing means `UnauthenticatedError` (the boundary rolls back, leaving the presented token unrevoked); (4) `createRefreshToken` with the replacement. Revoking the presented token and creating its replacement commit together or not at all; two concurrent rotations of one token cannot both succeed. After commit, sign the access token (async) and return the new session (user, access token, `expiresIn`, new raw refresh token).
  - `revokeSession(rawRefreshToken | undefined)`: never throws; absent or unknown is a no-op.
  - `verifyAccessToken(token)`: verifies signature (HS256) and expiry, returns `userId`, otherwise `UnauthenticatedError`. `requireAuth` calls this service; it never touches `jose` or repositories.
- **`AuthService`** (composed methods, D-18): `register`, `login` and `loginWithGoogle` each finish by calling `SessionService.issueSession` internally and return the complete session result (user, access token, `expiresIn`, raw refresh token); each router handler calls exactly one of them.
  - `register({ name, email, password })`: any existing account with that email (including Google-created) means `EmailAlreadyExistsError`; hash with argon2id; `createUser` (`provider = "email"`, `googleId = null`); a unique-violation race maps to `EmailAlreadyExistsError`; issue the session and return it; no profile is created.
  - `login({ email, password })`: unknown email, or account without a password, still runs one dummy verify against a fixed precomputed hash (timing equalization) and then throws `InvalidCredentialsError`; wrong password throws the same error with the same message; on success, issue the session and return it.
  - `loginWithGoogle({ idToken })`: verifier failure, `emailVerified !== true`, or unset `GOOGLE_CLIENT_ID` throws `InvalidGoogleTokenError` (a verified payload lacking `sub` or `email` is a verification failure reported by the adapter as `InvalidGoogleTokenError`, so the service never sees incomplete claims); normalize email to lowercase; resolution (1) by `googleId`, (2) by email: if that account's `googleId` is set and differs, throw `InvalidGoogleTokenError` and change nothing, otherwise `linkGoogleIdentity` (keeps `provider` and `passwordHash`), (3) create (`provider = "google"`, `passwordHash = null`, name from `resolveGoogleDisplayName`); on a unique-violation race, re-run resolution once. `resolveGoogleDisplayName`: trimmed token `name`; if absent or shorter than 2 characters, local part of the email; if that is shorter than 2, `"User"`. The session is then issued and returned.
  - `getCurrentUser(userId)`: unknown means `UnauthenticatedError`.
- **`PasswordResetService`**
  - `requestPasswordReset({ email })`: unknown email returns normally with nothing created and no mailer call; existing account (including Google-only): generate the raw token and its hash, then in one `TransactionRunner` boundary call `invalidateUnusedResetTokensForUser` and `createResetToken` (30-minute expiry) so at most one valid link exists even under concurrent requests; build `<frontendOrigin>/reset-password?token=<encoded raw>`, call `Mailer`; a mailer failure is logged server-side and never changes the response.
  - `resetPassword({ token, password })`: hash the new password (argon2, async) and compute `sha256(token)` before the boundary. Then, in one `TransactionRunner` boundary, in this order: `consumeResetToken`, `null` means `InvalidResetTokenError` (nothing changed); otherwise `updatePasswordHash` (a Google-only account gains its first password, `provider` unchanged), then `revokeAllRefreshTokensForUser`. If any step throws, none of the effects persist. No session is issued.

### 5.7 Security notes

argon2id with library defaults (parameters held in a named constant); CORS never uses `*` with credentials; access token carries `sub` only (plus `iat`/`exp` from the injected `Clock`); rotation and reset are atomic and race-safe through service-owned boundaries around single-table conditional UPDATEs; no password, raw token or refresh cookie value appears in logs (except the deliberate `ConsoleMailer` reset URL) or in error bodies (asserted by TU-26); no rate limiting or lockout is planned (none is specified and no library is approved); residual timing difference on forgot-password (existing account performs a write and a synchronous console log) is accepted.

#### 6.3.1 Session and auth infrastructure (FE-09)

- **State**: `AuthState` is a discriminated union `restoring | authenticated { user } | unauthenticated`. `useAuth()` returns `{ state, establishSession(session), clearSession(), logout() }`.
- **Token holder**: `token-store.ts` (`getAccessToken`, `setAccessToken`, `clearAccessToken`) is the only place the access token lives (D-15).
- **Restore on load**: `AuthProvider` starts in `restoring`, calls `refreshSession` once (single-flight, D-16), then moves to `authenticated` (token and user stored, renewal timer scheduled) or `unauthenticated` (on `401`, network error or `5xx`; no toast).
- **Proactive renewal**: after every establish or refresh, schedule a refresh at `max(expiresIn - ACCESS_TOKEN_REFRESH_LEAD_SECONDS, 0)` seconds; cleared on clear, logout and unmount.
- **Reactive renewal**: the auth-aware fetcher in `api-client.ts` sends `credentials: "include"` on every request. **Authorization rule:** it reads each operation's auth scheme from the contract (BE-01) and sends `Authorization: Bearer <token>` ONLY on operations whose contract security is Bearer (in this feature `getCurrentUser`, plus every protected endpoint later features add) and only when a token exists. It NEVER sends `Authorization` for `register`, `login`, `googleOAuthLogin`, `refreshSession`, `requestPasswordReset`, `resetPassword` or `logout`, even when a token exists (for example the proactive timer's `refreshSession`, a dashboard `logout`, or `resetPassword` with a local session, D-11). **Retry rule:** the retry applies exactly to requests that were sent with `Authorization`. On `401 UNAUTHENTICATED` for such a request the fetcher awaits the shared refresh, retries the original request once with the new token, and returns that result (a second `401` is returned, no loop); if the refresh fails it calls `clearSession()`. Because the seven operations above never carry `Authorization`, the retry can never apply to them: their `401`/`400` responses reach their own UI handling, and `refreshSession` can never recurse into itself or deadlock on the single-flight promise.
- **`establishSession`**: store token, set `authenticated`, schedule renewal. **`clearSession`**: clear token, cancel timer, `queryClient.clear()`, set `unauthenticated`. **`logout`**: call `logout`; regardless of outcome (including network failure) run `clearSession()` and navigate to `/auth`.
- **`api-client.ts`** builds the single ts-rest React Query client from the committed `@expense-tracker/contracts` package (from FE-09 onward) with `baseUrl` from `NEXT_PUBLIC_API_BASE_URL` (default `http://localhost:4000`) and the custom fetcher. It is the same client against the stubbed `fetch` during the Frontend session and against the real backend at Integration; there is no parallel or provisional client. No ad-hoc `fetch` anywhere else; the old hard-coded health-check fetch leaves with the old home page.
