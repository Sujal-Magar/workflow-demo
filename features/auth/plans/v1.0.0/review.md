## Blocking Findings

### B-1 · BE-02 CHECK constraint cannot be generated by the locked drizzle-kit, but T-UA-03 tests it

- **Plan:** §4 BE-02, `users` table: "table check: `password_hash` or `google_id` is not null". The same task says: "Generate the migration with drizzle-kit, commit it, and apply it at startup." §8.1 T-UA-03 expects: "the check constraint rejects a row with neither credential".
- **Spec:** FDS §3 `UserAuth`: "An account may have a `passwordHash`, a `googleId`, or both. It always has at least one of the two."
- **The problem:** `pnpm-lock.yaml` locks `drizzle-kit@0.24.2` and `drizzle-orm@0.33.0`. drizzle-orm 0.33 does have a `check()` builder for sqlite-core (`sqlite-core/checks`). drizzle-kit 0.24.2 ignores it. Its SQLite snapshot generator (`generateSqliteSnapshot` in `drizzle-kit/bin.cjs`) reads only `columns`, `indexes`, `foreignKeys`, `primaryKeys` and `uniqueConstraints` from `getTableConfig`, and the bundle never emits `CHECK`. So a migration generated as BE-02 instructs creates `users` **without** the constraint:
  - BE-02's own "Done when" still passes, because the three tables exist.
  - The gap first shows up in Phase 8, when T-UA-03 fails. The Unit/API agent then has to patch production code through the defect path.
  - Upgrading drizzle would need approval for a new library version (CLAUDE.md "No new libraries without explicit approval"; `rules/tech-stack.md`).
- **Checklist points:** 3 (cross-section consistency between Backend and Testing). The written approach cannot produce what the Testing section asserts, and choosing a fix is a real decision, so Build should not make it.

## Advisory Findings

- **A-1 · Root layout: client or server component.** §5 opens with "Every page and layout is a client component (CSR)." FE-01 and FE-11, however, make `app/layout.tsx` a logic-free shell that renders a separate client `providers.tsx`, which is the Server Component pattern. The existing `layout.tsx` also exports `metadata`, and Next 14 rejects that in a `"use client"` module. Obvious fix: state that `app/layout.tsx` stays a Server Component and keeps its `metadata` export, and that every other page and layout is a client component. The existing title is "Expense Tracker" while the FDS names the product "FinTrack". The FDS does not set a page title, so keep it unchanged unless the developer says otherwise.
- **A-2 · Coverage of the contract package's non-rule-set files.** Under D-22 and TH-01, `packages/contracts/src/**` gets coverage only from the package's own test run. Vitest's backend run leaves files outside `backend/` out of its report, and D-22 rejects `allowExternal`. T-UA-01 tests only the rule sets, so `auth-contract.ts`, `common/error-body.ts` and `index.ts` would show 0% unless a package test imports them. That counts against the 95% target at Phase 8c. Obvious fix: extend T-UA-01 so a test also imports `authContract` and checks all of the following:
  - For each of the eight routes: the method, the **full** path including `/api/v1/auth` (this checks BE-03's A-3 `pathPrefix` requirement directly), and the declared response statuses.
  - The error-code constant matches contract §3.
  - The shape schemas parse a valid example and reject an invalid one.
  - The package index re-exports the BE-03 public names.
- **A-3 · How the fetcher tells protected operations apart.** INT-02 retries "for protected operations only", and T-UI-09 tests that, but the plan never says how the fetcher classifies an operation. Integration cannot edit `packages/contracts/`, so it could not add route metadata at that point. Obvious fix: say in INT-02 that the fetcher holds an explicit list of the seven public and cookie auth routes, and treats every other operation as protected. That matches contract §7 ("later, every protected operation of other features"). The alternative is a route metadata flag added in BE-03.
- **A-4 · ts-rest React Query entry point.** The frontend has `@tanstack/react-query` 5.x and `@ts-rest/react-query` 3.52.1. That package ships a separate `./v5` entry point for TanStack Query v5. Naming it in INT-02 (`@ts-rest/react-query/v5`) saves Integration from finding out through type errors.
- **A-5 · CORS methods list.** Contract §8 `Access-Control-Allow-Methods` (`GET, POST, PATCH, DELETE, OPTIONS`) comes from the existing `index.ts` and leaves out `PUT`. This is fine for `auth`. A later feature that uses `PUT` will have to amend it. Informational only.
- **A-6 · `tailwind-merge` version (outside the plan's scope).** The existing `frontend/package.json` locks `tailwind-merge@3.6.0` next to `tailwindcss` 3.4. tailwind-merge 3.x targets Tailwind v4, and FE-01's `cn()` depends on it. Class merging for v3-only utilities may be wrong. This is a repository dependency question for the developer, not a plan defect. Worth checking at Phase 6.
