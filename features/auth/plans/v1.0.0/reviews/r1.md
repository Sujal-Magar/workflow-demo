## Verdict

**CHANGES REQUIRED**

The plan is thorough and the contract is complete. There are two blocking findings, and neither needs a change to `contract.md`:

- **B-1:** a signed-in visitor who resets their password is sent back to `/dashboard` and stays signed in. This contradicts REQ-AUTH-05.
- **B-2:** the owner of setup task S-01 is left as a three-way "or". Two of the three options conflict with the Build-mode path boundaries.

## Blocking Findings

### B-1 · A signed-in visitor who resets their password ends up on `/dashboard`, still signed in

- **Plan sections:** D-12, FE-10 (Restore), FE-11 (Guest-only route), FE-13 (Outcomes → Success), T-UI-07.
- **Spec:**
  - FDS REQ-AUTH-05 Step 2: "the user is redirected to `/auth` with the success toast … The user is not signed in automatically."
  - behavior §6 Reset page step 3: "redirect to `/auth?mode=signin` … other sessions are ended."
  - behavior §8: the session persists "until explicit logout, password reset, or refresh-token expiry."
- **Problem:** D-12 explicitly allows `/reset-password` to be opened by a signed-in visitor. The sections then combine like this:
  1. The `AuthProvider` sits in the root layout. On app load it restores the session (FE-10), so on `/reset-password` the status becomes `authenticated`.
  2. On reset success, FE-13 only shows the toast and calls `router.replace('/auth?mode=signin')`. It never clears the local session.
  3. The server has revoked all refresh tokens, but the in-memory access token is still valid for up to 15 minutes.
  4. The Guest-only route on `/auth` (FE-11) sees `authenticated` and calls `router.replace('/dashboard')`.
  5. The user sees "Password updated. Please sign in." while sitting on `/dashboard`, signed in. They are signed out only when the renewal timer fires and the refresh fails.
- **Why no test catches it:** T-UI-07 asserts "without establishing a session" but mocks the router and never starts from an existing session. T-UI-16 skips the valid-token path (D-10). INT-06 walks through the reset while signed out.
- **Classification:** **Obvious fix.** The specs fix the outcome: the user lands on `/auth` and is not signed in. The only way to reach that outcome from a signed-in state is to discard the local session.

### B-2 · The owner of setup task S-01 is unresolved, and two of the three listed owners break the Build-mode path boundaries

- **Plan sections:** D-01 ★, §2 Execution Order step 0 ("Build orchestrator, or the first individual Build run, or the developer"), §3 S-01.
- **Rules:**
  - CLAUDE.md Key Constraints: "Frontend Build touches only `frontend/`; Backend Build touches only `backend/` and `packages/contracts/`."
  - `.ai/prompts/build-mode.md`: Phase values are only `Frontend | Backend | Both | Integration`. Individual runs modify "only files under `frontend/`" (or "`backend/` and `packages/contracts/`"). Commits are "staged only from the paths your phase owns."
- **Problem:** S-01 must edit files that no Phase 5 role owns:
  - `pnpm-workspace.yaml`, where `allowBuilds` gets `argon2: true`. FDS §2 requires this.
  - `pnpm-lock.yaml`
  - `.env.example`
  - both `backend/package.json` and `frontend/package.json`

  If the developer confirms D-01 as written, a Phase 5 agent reading "the first individual Build run" would either break its scope, for example a `Phase = Backend` run editing `frontend/package.json` and root files, or stop and escalate mid-Build. No build prompt defines a "Build orchestrator" that writes files. The idea behind D-01 is sound: one serialized install avoids a lockfile race. What is missing is a single owner whose permissions allow the edit.

- **Classification:** **Developer decision.** More than one valid owner exists. See Suggested Next Step.

## Advisory Findings

These do not block approval. Items A-1 to A-4 are the most likely to cause a Phase 8 failure or a Diagnosis round, so consider folding them into the same revision.

- **A-1 · Single-use and rotation checks are check-then-act across an `await`.**
  - **Reset (BE-11):** the service looks up the token, then hashes the password (async argon2, before the transaction per BE-06), then marks the token used.
  - **Refresh (BE-10 / BE-07):** JWT signing with `jose` is async.
  - **Risk:** two concurrent requests with the same token can both pass the lookup. That breaks FDS §3 "a used token is invalid" and contract §4 "Presenting an already-rotated value returns 401."
  - **Fix:** inside the transaction, make "mark used" (`used_at IS NULL`) and "revoke one" (`revoked_at IS NULL`) conditional. If zero rows change, raise `InvalidResetTokenError` or `UnauthenticatedError`. Add one concurrency case each to T-UA-07 and T-UA-06.
- **A-2 · `type="email"` fields without `noValidate` hide the FDS inline messages.**
  - **Where:** FE-07, FE-08 and FE-12 use `type="email"`.
  - **Risk:** without `noValidate` on the `<form>`, the browser's native check blocks submit on a malformed email and shows its own tooltip. React Hook Form never runs, so the inline "Enter a valid email address." (FDS §5, AC4) never appears.
  - **Why tests miss it:** jsdom component tests don't show this, and T-UI-13 has no malformed-email case.
  - **Fix:** specify `noValidate` on every auth form, and add a malformed-email E2E case.
- **A-3 · Two `GoogleLogin` instances are mounted at once.**
  - **Cause:** FE-06 keeps both forms mounted, so there are two `GoogleLogin` instances (FE-09). Google Identity Services' `initialize` is global, and only the last call's callback is used.
  - **Risk:** success may run the hidden panel's handler. The FE-09 pending spinner and "disable the surrounding form's submit" would then hit the hidden form.
  - **Fix:** either keep Google sign-in state in one place (for example a single hook at `AuthCard` level shared by both buttons), or render the Google button only in the active panel.
- **A-4 · The error-mapping layer has no direct test.**
  - **Gap:** component tests mock `features/auth/api/auth-api.ts`. No test task targets FE-04 `auth-error.ts` or the INT-03 response mapping. That mapping holds a contract rule: an undeclared status or code for an operation becomes "unexpected" (contract §1, §7).
  - **Fix:** add a unit-test item covering every declared and undeclared status/code per operation, plus network failure. This also protects the 95% coverage target.
- **A-5 · Malformed JSON on no-body operations contradicts the contract.**
  - **Conflict:** contract §1 says "no body" operations (`/refresh`, `/logout`) ignore any body, and §6.6 says `logout` has no declared errors. But BE-14 applies the JSON parser globally, and BE-04 maps malformed JSON to `400 VALIDATION_ERROR`. T-UA-08 applies the malformed-JSON rule per operation.
  - **Fix:** limit the malformed-JSON rule and test to operations that take a body, or skip parsing for no-body routes.
- **A-6 · Coverage for `packages/contracts` is not defined.**
  - **Gap:** D-17 tests the shared rule sets from `backend/`. Vitest's coverage-v8 excludes files outside the project root by default (`coverage.allowExternal: false`), so the contract package would report no coverage at Phase 8c.
  - **Fix:** state how its coverage is collected: `allowExternal`/`include` in the backend config, or the package's own `vitest` config.
- **A-7 · Some plan-invented behavior has no test.**
  - BE-01 env validation: missing or short `JWT_SECRET` stops startup; `GOOGLE_CLIENT_ID` is required in production (D-08).
  - D-16 timing guard: a verify runs against the dummy hash for an unknown or password-less account. This can be asserted with a hasher spy.
  - behavior §6: the dialog closing on outside click and via the close control. T-UI-06 only tests Escape.
- **A-8 · Database and migration paths are ambiguous.**
  - **Database path:** BE-02 resolves `DATABASE_PATH` against the process working directory. Both `pnpm dev` and Playwright run in `backend/`, so the default `data/app.db` becomes `backend/data/app.db`. `rules/architecture.md` says `data/app.db`, so state which directory is meant.
  - **Migrations:** they live in `backend/src/db/migrations/**`, which `tsc` does not copy to `dist/`. Only `pnpm dev` is verified. Specify how the migrations folder is resolved so the built output also works.
- **A-9 · Reused dev servers can break the E2E Google assumptions.**
  - **Setting:** INT-07 keeps the existing `reuseExistingServer: !process.env.CI`.
  - **Risk:** locally, a dev server that is already running, possibly with Google configured or a different `JWT_SECRET`, is reused. That breaks D-11's assumptions for T-UI-17.
  - **Fix:** note that dev servers must be stopped before E2E, or set `reuseExistingServer: false` for this suite.
- **A-10 · Small gaps in the path table and the Phase 6 checklist.**
  - §2's Integration "May modify" column leaves out `pnpm-lock.yaml`, although INT-02/D-20 may add `@ts-rest/core`.
  - The Phase 6 checklist (§6) leaves out the toast look and position (an unstarred, invented choice: top right), the `/dashboard` placeholder, and the reset page's invalid-link state.
- **A-11 · The forgot-password dialog's reset on reopen is an unrecorded decision.** FE-12's "Every time it opens, it resets to an empty request step" is not in the specs or the Decision Log. It is harmless, but it should be recorded as a decision.

## Suggested Next Step

These are proposals for the developer, not decisions.

### 1. Classification

**B-1 · Obvious fix.** Changes:

- **FE-13:** on success, call the FE-10 `clearSession()`, then show `PASSWORD_UPDATED_TOAST` and call `router.replace('/auth?mode=signin')`. `clearSession()` empties the token store, cancels the renewal timer, clears the query cache and sets the status to `unauthenticated`. Do not call `logout()`: the server has already revoked every refresh token, and `logout()` redirects to `/auth` without `mode`.
- **D-12:** state that a signed-in visitor's local session is cleared on reset success.
- **T-UI-07:** add a case that starts from an authenticated session and asserts that after success the status is `unauthenticated` and the token store is empty.
- **Optional:** an E2E case in T-UI-15 or T-UI-16. Signed-in → open `/reset-password?token=bogus` → the invalid-link state shows. This checks that D-12's no-guard rule works in the browser.

**B-2 · Developer decision.** **DECISION NEEDED:** who runs S-01.

| Option | Owner                                                                                                                            | Trade-off                                                                                                                                                                          |
| :----- | :------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A      | **The developer, by hand, before Phase 5** (`pnpm add …`, edit `pnpm-workspace.yaml` and `.env.example`, `pnpm install`, commit) | No prompt changes, keeps every agent inside its boundary, one clean commit. Costs a few minutes of manual work. The plan must remove the other two owners and give exact commands. |
| B      | **A dedicated one-off agent session** ("Setup"), given S-01 as its whole task and explicit permission for those five files       | Automated, and it keeps Build agents in scope. But it runs outside any documented workflow phase and prompt, so the plan must spell out that session's boundary and log line.      |
| C      | **The Integration agent** (it already may stage everything), with Phase 5 builds relying on dependencies being installed         | Not workable. Phase 5 needs `argon2`, `jose`, `google-auth-library`, `cookie-parser` and `@react-oauth/google` before Integration runs. Listed only to rule it out.                |

**Recommendation:** Option A. It needs no change to `.ai/prompts/` or `rules/`, and argon2's native build is best confirmed by a person anyway.
