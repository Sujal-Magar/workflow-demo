## Blocking Findings

### B-1 — Repositories carry business rules and a cross-aggregate workflow (rule conflict)

- **Plan:** §5.5 `PasswordResetTokenRepository.completePasswordReset` consumes the token, sets `users.password_hash`, and revokes all of that user's `refresh_tokens` in one repository call. §5.5 `RefreshTokenRepository.rotateActiveRefreshToken` encodes the rotation rule (revoke only if active and unexpired, then insert the replacement). §5.6 `resetPassword` is reduced to "hash the password; call `completePasswordReset`; `null` means `InvalidResetTokenError`". §1.3 nevertheless claims full layering compliance.
- **Rule:** `rules/architecture.md` — Repository Layer: "MUST NOT contain business rules". Service Layer: "Coordinate multi-step workflows". Transactions: "**Services define transactional intent and boundaries.** Repositories execute transactional operations". `rules/conventions.md` — repositories are small, feature-specific, persistence-only.
- **Spec:** REQ-AUTH-05 step 2 and REQ-AUTH-06 (rotation) define the "reset ends every session" and "rotation revokes the presented token" behaviors. Those are the domain rules the architecture assigns to services. `completePasswordReset` also writes to two tables that other repositories own.
- **Why it blocks:** The reset and rotation workflows are the security core of this feature, and this feature sets the layering pattern later features reuse (D-17). Build would otherwise follow a pattern the Approval Gate never explicitly accepted.
- **Required change:** Either
  - (a) keep the service as the workflow owner. Introduce a transaction-boundary mechanism the service controls (for example a transaction-runner port). Repositories then expose single-table intention-revealing operations, such as `consumeResetToken`, `updatePasswordHash` and `revokeAllRefreshTokensForUser`, and `revokeActiveRefreshToken` returning a boolean; or
  - (b) add an explicit ★ decision to the Decision Log that atomic multi-step persistence operations may live in repositories. This asks the developer to accept a deviation from `architecture.md`, and §1.3 must stop claiming full compliance.

### B-2 — How Frontend Build obtains the contract schemas and API client during the parallel phase is undefined

- **Plan (contradictory statements):**
  - §6.1 says the frontend "never edits `packages/contracts`", uses provisional local types "that exist only in the mocks", and builds against `lib/auth/api-client.ts` "backed by mocks".
  - §6.3.1 says `api-client.ts` "builds the single ts-rest React Query client **from the shared contract**".
  - §6.5, 6.6, 6.9 and 6.12 require React Hook Form with "the contract sign-up schema", contract reset schema and so on, and say the frontend "defines no field message strings".
  - §5.3 (Backend Build order) says BE-01 is first "because Integration **and the frontend** depend on its exports".
  - §4 and §9 say the sessions run in parallel without seeing each other's work.
  - FE-12 lists fixtures for shapes and errors but no schema or message fixtures.
  - `packages/contracts/src/index.ts` is currently `export {}`.
- **Conflicts with:** `CLAUDE.md` Key Constraints and `rules/architecture.md` (API Contracts: no duplicate request/response types; frontend uses ts-rest clients from the contracts package); FDS §5 ("messages are defined once, in the shared schemas in `packages/contracts`"). Checklist points 3 and 6.
- **Why it blocks:** The FE-05 forms are the subject of the Phase 6 UI review, and their inline validation cannot work without schemas and verbatim messages. The plan gives no source for them until INT-01. An agent will either invent local schemas (silently duplicating FDS strings) or stall waiting for BE-01.
- **Required change:** State one explicit mechanism in §4 and §6.1:
  - (a) BE-01 is committed first and the Frontend session starts from it. This is a written sequencing dependency, not fully parallel; or
  - (b) FE-12 gains temporary local schemas carrying the exact FDS §5 strings, plus a temporary client shim, both deleted in INT-01. Record the temporary duplication as a ★ decision.

### B-3 — Delivery of frontend environment variables is unspecified and, as written, does not work

- **Plan:** D-4, P0-3 and the §7 environment matrix put `NEXT_PUBLIC_GOOGLE_CLIENT_ID` and `NEXT_PUBLIC_API_BASE_URL` into the repo-root `.env.example` (and so a root `.env`). §6.7 and INT-06 rely on the Google variable reaching the browser bundle.
- **Repo fact:** Next.js loads `.env*` only from the app directory (`frontend/`). No `frontend/.env*` exists, `next.config.mjs` loads nothing, and only the backend's `index.ts` probes parent-directory `.env` paths. A root `.env` never reaches Next, so the Google button would always show the "unavailable" fallback, and INT-06's configured-path check could not pass.
- **Spec:** FDS §2 (client ID read from `NEXT_PUBLIC_GOOGLE_CLIENT_ID`); REQ-AUTH-03 frontend states.
- **Required change:** Decide where frontend variables live (for example `frontend/.env.local`, already git-ignored, with a documented `frontend/.env.example`, or an explicit load in `next.config.mjs`). Add that file to P0-3 and to the P0 "may touch" list in §9. Cover the Playwright frontend `webServer` env for TE-14.

### B-4 — Phase 6 UI checkpoint timing and scope are inconsistent

- **Plan:** The FE-05 row says "Phase 6 UI review checkpoint is **after this task**". The build order then continues with FE-06 (Google button), FE-07 (forgot dialog) and FE-08. §4 says Phase 6 is "after FE-05 **and the rest of the frontend build**". `CLAUDE.md` says Phase 6 is "After frontend build completes".
- **Spec:** The sign-in and sign-up visuals both show the Google control, and REQ-AUTH-01/02 place it in both forms. Per §6.5 and §6.6, the FE-05 forms embed `GoogleSignInButton` (built in FE-06) and the forgot-password trigger (dialog built in FE-07).
- **Why it blocks:** As written, the human freezes the UI at a point where required visual elements do not exist yet, or the frontend session must pause mid-build for a gate the workflow places after build completion.
- **Required change:** Make one statement (in the FE-05 row and §4) of when the freeze happens and what is in scope. Recommended: Phase 6 runs after all FE tasks. If an early look is wanted, label it an informal preview and state that it does not freeze the UI.

## Advisory Findings

1. **Router composition vs "exactly one service method" (BE-12 vs D-18).** BE-12 says each handler calls exactly one service method. D-18 lets the router call `issueSession` after `register`, `login` or `loginWithGoogle`, which is a two-step workflow in Presentation (`architecture.md`: Presentation stays thin, services coordinate). Recommend picking the composed-service option now so BE-12 and D-18 agree. A user-created-then-session-failure gap also disappears.
2. **CORS methods regress existing behavior (BE-04).** The current middleware allows `GET, POST, PATCH, DELETE, OPTIONS`. BE-04 narrows this to `GET, POST, OPTIONS`, while contract §6 says only "includes". Later features' CRUD endpoints will need PATCH/DELETE (and likely PUT). Keep the existing methods.
3. **Database path base (BE-02, INT-04).** `architecture.md` fixes the database at `data/app.db`. The default `./data/app.db` is relative to the process cwd, which is `backend/` under `pnpm dev` and the Playwright `webServer` (`cwd: "backend"`). That yields `backend/data/app.db`. State the resolution base explicitly (for example repo root) or accept `backend/data` as a documented decision.
4. **Non-object JSON bodies (contract §1 vs §5/R3, BE-03, TU-13/TU-21).** §1 says a body that is not a JSON object is treated as an empty object, so every field reports "required". `express.json()` in strict mode rejects JSON primitives (`"abc"`, `123`, `null`) as a parse error, which R3 maps to `VALIDATION_ERROR` with empty `fieldErrors`. Specify which behavior applies to valid-JSON non-objects. No frontend impact.
5. **Google claim edge cases.** The `GoogleTokenVerifier` claims are `{ sub, email, emailVerified, name? }`, but the plan does not say what happens if `sub` or `email` is absent in the payload (recommend `InvalidGoogleTokenError`). It also does not say what `GoogleLogin.onSuccess` does when `credential` is undefined (recommend treat as dismissal: no request, no toast).
6. **Sharing the "Google unavailable" flag (§6.7 vs §6.2).** `GoogleOAuthProvider` is mounted in `providers.tsx`, but the flag set by `onScriptLoadError` is described as "local". Specify the context or state that carries it to `GoogleSignInButton`. The provider also loads Google's script on every page, including `/dashboard`.
7. **Clock injection into the JWT adapter (BE-08).** TU-08, TU-09 and TU-18 test access-token expiry "by clock". The `AccessTokenSigner` port and `JoseAccessTokenSigner` must issue and verify against the injected `Clock` (for example jose's `currentDate`). The plan does not state this.
8. **Clearing the cookie on refresh 401 (BE-12).** The contract requires every `refreshSession` 401 to carry a clearing `Set-Cookie`, but errors go through a global `error-mapper`. State how the refresh route's error path clears the cookie (TU-14 verifies the result, not the mechanism).
9. **Protected routes other than `/dashboard` (§6.10, REQ-AUTH-07).** The plan says the guard "covers" `/transactions`, `/budget`, `/goals`, `/reports` and `/profile`, but those pages do not exist yet, so an unauthenticated visit produces a Next 404, not a redirect. This is consistent with the FDS placeholder scope. Say so explicitly, and note that only `/dashboard` is verifiable (TE-10) until the other features add pages under `(protected)`.
10. **Untested decisions.** D-6 (stacked mobile layout, no slide animation) has no component test. D-8 (name trimming) has no frontend case in TC-3 (whitespace-only name). No test asserts that raw tokens and passwords never reach server logs (§5.4).
11. **Traceability nit.** BE-03 and BE-13 cite only D-17 (a plan decision), not an FDS section. BE-13 could cite FDS §3 and §6. All other tasks cite a requirement or FDS section.
12. **Abstraction count.** Five ports plus `Clock` and id/token generators. This is justified for network-free and time-controlled tests (and `Mailer` is FDS-mandated). Confirm at the Approval Gate that `PasswordHasher` and `AccessTokenSigner` ports are wanted, given `conventions.md` ("avoid unnecessary abstractions").
13. **Sliding animation vs unmount-on-switch (§6.4).** Only the active form is mounted, so the outgoing form disappears at once while the overlay is still sliding over its slot (a blank flash). Consider a brief overlap or fade. This is presentation only.
14. **FDS-level observations (informational, not plan defects).** The FDS-mandated account linking (REQ-AUTH-03 step 2) links a Google identity to an email/password account whose email was never verified, and a 409 on registration reveals an existing email. The plan implements the FDS faithfully. The developer may want to record these as accepted risks (no email verification exists; `rules/tech-stack.md` forbids external email).
