## Blocking Findings

### B-1. INT-03 tests the reactive 401 retry against `getCurrentUser`, which the plan's own client excludes from retry

- Plan section 6.3.1 (Reactive renewal): "The retry path is skipped for the eight auth operations so a `401` from them reaches their own UI handling." TC-35 asserts the same ("the eight auth operations never trigger the retry").
- `getCurrentUser` (`GET /api/v1/auth/me`) is one of those eight operations (contract section 4, FDS section 6).
- Plan section 7, INT-03: "reactive `401` retry against a real protected call (use `getCurrentUser` with an expired or tampered token)".
- These cannot both hold. As written, INT-03 can never observe a retry, and the frontend does not call `getCurrentUser` at all (contract 4.5). TE-15 concedes "if no protected call exists in scope ... covered by TC-35 only", and no other protected endpoint exists in this feature.
- Spec basis: FDS REQ-AUTH-06 (Renew: "once after a `401 UNAUTHENTICATED` response from any protected endpoint, and retries the original request once") and REQ-AUTH-08; behavior.md section 7.
- Why it blocks: Integration Build would hit the contradiction mid-build and must choose between changing the retry rule (client design) and changing the test (verification design). It is a plan-level decision, not something Integration may patch (it may not change frozen shapes).
- Needed: state one rule explicitly. Either (a) exempt only `login`, `register`, `googleOAuthLogin`, `refreshSession`, `logout`, `requestPasswordReset` and `resetPassword` from retry and treat `getCurrentUser` (Bearer) as a protected call, updating 6.3.1, TC-35 and its "eight" wording; or (b) keep the exemption and change INT-03 and TE-15 to verify the reactive retry differently (for example a test-only protected probe in the integration harness, or explicit "verified by TC-35 only; no real protected endpoint exists until another feature lands").

## Advisory Findings

**A-1. Local `.env` needs `JWT_SECRET`; the plan only updates `.env.example`.** The developer's root `.env` (git-ignored, not touched by P0-3) contains only `PORT`, `FRONTEND_ORIGIN`, `DATABASE_PATH`. With D-2 (fail fast), `pnpm dev` will refuse to start after the backend build until the developer adds a 32+ character secret. Playwright is unaffected (it passes the secret through `webServer.env`). Add a line to the P0 exit check or INT-04 telling the developer to add `JWT_SECRET` to their `.env`.

**A-2. Section 1.3 overstates Drizzle isolation.** It says only `auth/repositories/` imports Drizzle. Per section 5.2, `db/client.ts`, `db/migrate.ts`, `db/schema/*` and `backend/drizzle.config.ts` also import Drizzle or better-sqlite3. This is compliant with `rules/architecture.md` (Database layer, and only repositories issue queries), but the sentence should say "only repositories and the `TransactionRunner` implementation run queries" so a later compliance audit does not misread it.

**A-3. TU-07 case is not constructible as specified.** "A deleted user leaves the presented token unrevoked (boundary rolled back)" requires a `refresh_tokens` row whose user is gone, but section 5.4 declares an enforced FK on `refresh_tokens.user_id` with no cascade and `foreign_keys = ON`. The test must disable the pragma for that test (say so), or the step-(3) case should be tested by stubbing `findUserById`. Also note that step (3) is otherwise unreachable defensive code.

**A-4. `/transactions`, `/budget`, `/goals`, `/reports`, `/profile` are not redirected today (section 6.10).** FDS REQ-AUTH-07 and behavior.md section 8 say unauthenticated access to these redirects to `/auth`; the plan delivers this only by construction of the `(protected)` group, so today those paths are a Next.js 404. The plan writes this down, but it is not in the Decision Log or the gate confirmations (section 10), and the acceptance criterion is only verifiable for `/dashboard`. Add a starred decision so the developer accepts it explicitly.

**A-5. D-19 log-capture location is unspecified.** The E2E backend log file path is not named. Pick a git-ignored location (for example under `test-results/`) so a test run does not leave untracked files. If `reuseExistingServer` picks up an already-running backend, no log exists; the stated fallback covers it, but TE-13 should say the real-loop case is skipped in that situation.

**A-6. Contract gaps that Build would decide silently.** (i) Contract section 3 defines the not-a-string case only for `token`; a non-string `name`, `email`, `password` or `confirmPassword` has no stated message or key behavior. (ii) The contract trims `email` before validation (sections 3 and 9-R7), which extends the FDS beyond the name-trimming decision recorded in D-8 and 10-A1; record it as an advisory item or a starred decision. (iii) Error `message` text per code is unspecified (clients branch on `code`, so this is safe, but tests such as the "byte-identical 401" in TU-16 rely on it being constant).

**A-7. Placeholder and copy details from the visuals are not written down.** The PNGs show placeholder text `Name`, `Email`, `Password`, `Confirm Password` with no visible labels; sections 6.5 and 6.6 list fields and icons but never state placeholders (only "visually hidden Label"). Reset dialog and reset page copy is covered by D-5 but the placeholders for those fields are also unstated. Add them so Phase 6 review does not turn on unwritten copy.

**A-8. D-23 deviates from `.ai/prompts/build-mode.md` and relies on manual sequencing.** The build prompt has the Frontend subagent building on mock data and the Backend subagent generating contracts; the plan has Frontend consume the committed contracts package over a stubbed `fetch` and requires the orchestrator to hold the Frontend session until the BE-01 commit exists. This is explicit, starred and rationalised, so it is not blocking; the developer should confirm knowing that "Phase = Both" as a single fan-out cannot be used unchanged.
