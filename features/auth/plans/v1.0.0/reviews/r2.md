## Verdict

**CHANGES REQUIRED**

The plan is thorough and meets six of the seven checklist points. It fails on Testability: as written, the Phase 8c coverage target (95%, FDS frontmatter) cannot be measured, and with the planned test placement it cannot be reached. Both problems are cheap to fix now. Found at Phase 8c, they would send a finished feature into the Diagnosis loop.

---

## Blocking Findings

### B-1 · The shared contract package's auth code will have no measured coverage at Phase 8c

- **Plan location:** §1 D-17; §8.1 test harness and T-UA-01; §8 intro ("Coverage target is 95% for auth code … checked at Phase 8c"); §2 path ownership (Unit/API agent: `backend/**` tests only).
- **Spec / rule:**
  - FDS frontmatter `coverage_target: 95`.
  - `rules/workflow.md` §2 Phase 8 exit ("Coverage meets the threshold declared in `fds.md`") and Phase 8c.
  - `sonar-project.properties`: `sonar.sources` includes `packages/contracts/src`, and `sonar.javascript.lcov.reportPaths` expects `packages/contracts/coverage/lcov.info`.
- **Problem:** BE-03 puts real auth logic in `packages/contracts/src/auth/`: the six rule sets, the six composed sets, first-failing-rule ordering, the "absent → empty message" handling and the always-run `confirmPassword` match. D-17 moves every test of that code into `backend/`. That choice has two effects:
  - Vitest's v8 coverage ignores files outside the project root by default (`coverage.allowExternal: false`, unchanged in `backend/vitest.config.ts`). The backend run therefore records nothing for `packages/contracts/src/**`.
  - No task produces `packages/contracts/coverage/lcov.info`. The package has no tests, and under `.ai/prompts/test-build-mode.md` no test agent may write there.

  Sonar will count the contract package as uncovered new code. It is a sizeable share of the feature's executable lines, so 95% is out of reach even if every other file is fully covered. The plan records where the tests live (D-17) but never says how their coverage is attributed.

- **Classification:** Developer decision (see Suggested Next Step).

### B-2 · No task configures the LCOV coverage output that the Full Quality Gate reads

- **Plan location:** §8 Testing Section (the harness descriptions in §8.1 and §8.2); no task covers coverage configuration.
- **Spec / rule:** `rules/workflow.md` §2 Phase 8c and §7 (Full Quality Gate uses coverage); `sonar-project.properties` (`frontend/coverage/lcov.info`, `backend/coverage/lcov.info`).
- **Problem:** `backend/vitest.config.ts` and `frontend/vitest.config.ts` set no `coverage` options. Vitest 2's default coverage reporters are `text`, `html`, `clover` and `json`, which do not include `lcov`. So `pnpm test:coverage` writes no `lcov.info`, and the gate sees no coverage at all. The plan states the 95% target and says it is "checked at Phase 8c", but no Build or Test task makes the result measurable.
- **Classification:** Obvious fix. `sonar-project.properties` fixes the format and paths, so only one answer is correct. Both config files already sit inside the Unit/API scope (`backend/`) and the UI/E2E scope (`frontend/`).

## Advisory Findings

- **A-1 · Untested modules put pressure on the 95% target.** With `coverage.all` at its default, every file under each `src/` counts. Several planned files have no listed test:
  - Backend: `backend/src/config/env.ts` (BE-01, including D-08 "GOOGLE_CLIENT_ID required in production" and the `JWT_SECRET` ≥ 32-character rule), `backend/src/index.ts` wiring and `backend/src/db/migrate.ts`.
  - Frontend: `app/layout.tsx`, `app/providers.tsx`, the thin `app/**/page.tsx` wrappers, `fintrack-logo.tsx`, `brand-panel.tsx`, `full-page-loader.tsx` and `lib/env.ts`.

  Recommendation: add small tests for `env.ts` (missing `JWT_SECRET`, short secret, production without `GOOGLE_CLIENT_ID`), and render tests for the providers, the page wrappers and the presentational pieces. The alternative is a written decision on which files are excluded from coverage. Excluding files changes `sonar-project.properties`, and only the developer can make that edit.

- **A-2 · INT-02 ↔ FE-10: no mechanism for the fetcher to end the session.** INT-02 has the module-level fetcher in `lib/api-client.ts` "clear the session and redirect to `/auth`" when the refresh or the retry fails. In FE-10, `clearSession()` lives in the React `AuthProvider` and needs the router and the QueryClient. The plan does not say how the fetcher reaches them, for example through a session-expired listener that `AuthProvider` registers on the module-scoped token store. Both tasks are owned by the frontend and Integration, so this cannot cause a cross-team mismatch. Writing the mechanism into FE-10 would still save Integration a design decision.

- **A-3 · Database path base is left implicit.** BE-02 resolves `DATABASE_PATH` "against the process working directory". The backend always runs with its working directory set to `backend/`: `pnpm -r dev`, and Playwright's `cwd: "backend"`. The files therefore land in `backend/data/app.db` and `backend/data/e2e-test.db`. `rules/architecture.md` and `rules/tech-stack.md` say `data/app.db`, and the comment in `sonar-project.properties` ("data (backend runtime db)") suggests backend-relative was intended. Stating the resulting location in BE-02 would remove the ambiguity.

- **A-4 · The INT-07 / D-11 E2E environment is not guaranteed.** `playwright.config.ts` has `reuseExistingServer: !process.env.CI`. Outside CI, Playwright reuses whatever dev servers are already running, with the developer's `.env`, `app.db` and possibly Google configured, and silently skips the INT-07 environment. Also, `backend/src/index.ts` loads the root `.env`, which can supply `GOOGLE_CLIENT_ID` whenever Playwright does not set it. Neither changes a test outcome today, because T-UI-17 never reaches the backend. Consider having INT-07 set `reuseExistingServer: false`, or require `CI=1` for Phase 8 E2E runs.

- **A-5 · Minor test gaps against behavior and the contract:**
  - behavior §6 step 1 says the dialog closes "on outside click, and via a close control". T-UI-06 only tests Escape.
  - contract §1 says "Unknown body fields: ignored … never echoed". No T-UA test sends one.
  - D-16 (dummy-hash timing guard) has no test. A test could check that `verify` is called on the unknown-email and no-password paths.

- **A-6 · A JSON body that is not an object is unspecified.** contract §5 says absent fields report their "empty" message. With a body such as `[]` or `"x"`, a Zod object schema fails at the root, not per field, and produces no per-field `fieldErrors`. Stating the behavior would close the gap, for example: a non-object body is treated as `{}`, or it returns `VALIDATION_ERROR` with empty `fieldErrors`, like malformed JSON.

- **A-7 · The email format rule is not pinned.** contract §5 says "not of the form `local@domain.tld`" but does not say whether that means Zod's built-in `.email()` or a specific pattern. Both sides share one schema, so they cannot disagree. The expected results for edge cases (`a@b.c`, `a@localhost`, `a@b..com`) are still undefined for T-UA-01 and T-UI-13.

- **A-8 · FE-06 `inert` with React 18.** React 18's type definitions do not include an `inert` prop, and React 18 does not pass a boolean `inert` through reliably. Under strict TypeScript, and with the conventions' ban on `any`, FE-06 should say how to apply it, for example by setting the attribute through a ref.

- **A-9 · D-13 should be starred.** FDS REQ-AUTH-07 and AC14 name `/transactions`, `/budget`, `/goals`, `/reports` and `/profile`. Until those features ship, those URLs return a Next 404, not a redirect to `/auth`. Phase 9 validation of AC14 for `auth` will only cover `/dashboard` and `/`. That follows from the FDS placeholder text, but the developer should accept it knowingly.

- **A-10 · Only the dev runtime is verified.** Three things will break a production build:
  - BE-02 applies migrations at startup, but `tsc` (the backend `build` script) does not copy `backend/src/db/migrations/**` to `dist/`.
  - `@workflow-demo/contracts` exposes TypeScript source (`main: ./src/index.ts`), which `node dist/index.js` cannot load.
  - Every done-criterion uses `pnpm dev`/tsx, so none of this is exercised.

  This is out of scope for the FDS. A one-line note in §1 "Known limitations" would stop anyone assuming `pnpm build && node dist` works.

- **A-11 · Small plan-level choices missing from the Decision Log:**
  - BE-01's `JWT_SECRET` minimum of 32 characters.
  - INT-02 clears the session when the retry after a successful refresh also returns 401.
  - FE-12 resets the dialog on every open.
  - FE-03's toast timing and position.

  All are reasonable. Listing them unstarred in §1 would keep the rule that anything not in the plan is not decided.

## Suggested Next Step

The specs are sound. Both blocking findings concern the Testing section. Neither touches `contract.md` or the Frontend/Backend build tasks, beyond §2 path ownership if option A is chosen for B-1.

### Classification

**B-2 · Obvious fix.**

- Add a Phase 8 harness step to §8. The Unit/API agent sets `coverage.reporter` in `backend/vitest.config.ts` and the UI/E2E agent sets it in `frontend/vitest.config.ts`.
- Each reporter list includes `lcov` (plus `text`) and writes `coverage/lcov.info`, the paths `sonar-project.properties` reads.
- Add a done-criterion: `pnpm test:coverage` produces both files.

**B-1 · Developer decision: DECISION NEEDED.** How is coverage of `packages/contracts/src/auth/**` collected?

- **Option A: contract-package tests live in the package (recommended).**
  - Move the T-UA-01 rule-set tests to `packages/contracts/src/**/*.test.ts`, run by the package's existing `vitest.config.ts`.
  - Add a `coverage.reporter` that includes `lcov`, so `packages/contracts/coverage/lcov.info` exists as `sonar-project.properties` expects.
  - Drop D-17.
  - _Trade-off:_ the Unit/API scope in `.ai/prompts/test-build-mode.md` is "strictly `backend/`", so the developer must widen it to `backend/` plus test files under `packages/contracts/`. That matches Backend Build, which already owns `packages/contracts/`. The attribution is clean and it works for every later feature's contract code.
- **Option B: keep the tests in `backend/` (D-17) and collect external coverage.**
  - Set `coverage.allowExternal: true` and `coverage.include` covering `../packages/contracts/src/**` in `backend/vitest.config.ts`.
  - _Trade-off:_ no scope change. The LCOV entries become `../packages/…` paths relative to `backend/`, and Sonar's handling of them needs checking. The package's own `test:coverage` run may still emit a 0% report for the same files, so the two reports could conflict. This is the riskiest option to verify.
- **Option C: exclude the contract package from coverage** (`sonar.coverage.exclusions=packages/contracts/**`).
  - _Trade-off:_ the smallest change, but the developer must edit `sonar-project.properties`, which is outside every agent's scope. The code that enforces the FDS §5 messages would go unmeasured, which lowers the bar the FDS set with `coverage_target: 95`.

Recommendation: **Option A**. It is the only option whose coverage attribution needs no path tricks. It also fixes the problem for every later feature that adds contract code.
