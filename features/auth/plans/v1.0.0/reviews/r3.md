# Plan Review: Authentication and Identity (`auth`) v1.0.0

Reviewed: `plan-v1.0.0.md` (revision 2) and `contract-v1.0.0.md` (revision 2), as on disk on 2026-09-25.
Reviewed against: `features/auth/fds.md`, `behavior.md`, `visuals/auth-signin-page.png`, `visuals/auth-signup-page.png`, `rules/architecture.md`, `rules/conventions.md`, `rules/tech-stack.md`, `features/index.json`, and the current repository state (verified directly, not taken from the plan).

## Verdict

**CHANGES REQUIRED**

Two blocking findings. Both are small textual fixes, but each is a real defect: one is a contradiction between two sections of the plan, the other is a literal conflict between the contract and `rules/conventions.md`. No spec-level ambiguity or contradiction was found (FDS, behavior spec and visuals are mutually consistent), so this is a plan/contract problem, not an escalation to the developer.

## Blocking Findings

### B-1. Reactive-retry rule contradicts the fetcher's Authorization behavior (cross-section inconsistency)

- Plan section 6.3.1 (FE-09, "Reactive renewal") says the auth-aware fetcher sends `Authorization: Bearer <token>` **"when a token exists"** on every request. TC-36 (section 8.2) asserts the same: "`Authorization` only when a token exists".
- The same paragraph defines the 401 retry rule "by the Authorization header": it applies only to requests "sent with a Bearer access token" and is "skipped for the seven operations that never carry a Bearer token" (`register`, `login`, `googleOAuthLogin`, `refreshSession`, `requestPasswordReset`, `resetPassword`, `logout`). TC-35 asserts that those seven "never carry one" and "`refreshSession` never recurses".
- These cannot all hold. When a token exists (which is exactly when the proactive-renewal timer, `logout` from the dashboard, or `resetPassword` with a local session, D-11, fire), the fetcher as specified attaches a Bearer header to those seven operations, so they are not "never carry" requests. By the header-defined rule they would then be retried on `401`. Concretely: the proactive timer calls `refreshSession` with a token in memory, the server returns `401`, the fetcher treats it as a Bearer-carrying request, calls the shared single-flight refresh (which is the request already in flight), and deadlocks or recurses. This is the exact hazard the rule was written to prevent.
- TC-35 and TC-36 as written cannot both pass against one implementation: TC-36 requires the header on any request when a token exists; TC-35 requires none of the seven to carry it.
- Spec side: FDS REQ-AUTH-06 and the contract (4.4: "no `Authorization` header is needed or read") give no basis for choosing either behavior, so Build would be deciding this silently.
- Fix needed: state one behavior explicitly. Either the fetcher omits `Authorization` for the seven auth operations (and TC-36 is reworded accordingly), or the retry decision uses an explicit per-request flag instead of "was a Bearer header sent". Then make FE-09, 6.3.1, TC-35 and TC-36 agree.

### B-2. Contract default `INTERNAL_ERROR` message violates `rules/conventions.md`

- Contract section 5 ("Informational `message` text per code") fixes the default message for `INTERNAL_ERROR` as `Something went wrong`. Plan BE-12 and section 5.3 route unknown errors to `500 INTERNAL_ERROR` with a "generic message".
- `rules/conventions.md`, "Error Handling": "Avoid generic error messages like 'Something went wrong'." The contract prescribes that exact string, and contract 2.5 also says messages are "actionable". The contract is frozen at the gate and Backend Build must follow it verbatim, so the conflict would be built in.
- The wording is not a spec requirement (FDS lists no 500 code; the contract calls it a non-normative default, 10-A3), so replacing it with a non-banned, non-leaking sentence (for example one that says the server could not complete the request and to retry later) costs nothing. The "one fixed string per code, leaks nothing" property is preserved.

## Advisory Findings (8, non-blocking)

1. **`@ts-rest/core` is not a direct dependency of `frontend` or `backend`, and P0-1 says "nothing else is added".** Verified: neither package.json lists it (only `@ts-rest/express` and `@ts-rest/react-query`), and neither `node_modules/@ts-rest/` contains `core`. The custom fetcher and imperative refresh path (FE-09: session refresher called outside React, `ApiFetcher`/`tsRestFetchApi` types) and the backend validation-error handler (BE-12) will very likely need to import from it. It is already approved in `rules/tech-stack.md`, so this is a P0-1 wording/scope gap, not a new library. Decide at the gate whether P0-1 adds it.
2. **Next.js consuming a TypeScript-source workspace package is not planned for.** `packages/contracts/package.json` has `main: ./src/index.ts` and `frontend/next.config.mjs` has no `transpilePackages`. `pnpm build` (INT-07) and dev may fail to compile the contracts package. Not verified by a build (the contracts package is empty today). It is fixable within the Frontend boundary (`next.config.mjs`), but the plan should list it. (A backend `tsc` check with the package resolved through `node_modules` passed in a throwaway probe, so the backend side looks fine.)
3. **E2E environment overrides are silently ignored under `reuseExistingServer`.** The existing `playwright.config.ts` uses `reuseExistingServer: !process.env.CI`. Only TE-13's real-loop case is guarded (D-19). TE-14 and TE-16 depend on `webServer.env` (`NEXT_PUBLIC_GOOGLE_CLIENT_ID` empty), and every E2E depends on the backend's `JWT_SECRET` and `DATABASE_PATH`; a developer's already-running servers would change the outcome. Also, D-19's log redirect needs the `test-results/` directory to exist and a shell redirect in `command`; neither is stated.
4. **TC-44 presumes a JavaScript-driven breakpoint that FE-04 and D-6 do not specify.** jsdom does not evaluate Tailwind `md:` variants, so "no slide-transition classes applied below `md`" is only testable if the card switches layout in JS (matchMedia hook). Say which approach FE-04 uses, or reword TC-44.
5. **TU-25's async-callback guard is left to "Build's chosen guard".** Section 5.5 only says the callback is "typed as synchronous". Either specify the runtime behavior (for example throw if the callback returns a promise) or drop the runtime assertion.
6. **Protected-route acceptance is an explicit but weakly surfaced decision.** FDS REQ-AUTH-07 and behavior section 8 list `/transactions`, `/budget`, `/goals`, `/reports`, `/profile` as redirecting to `/auth`; the plan (6.10, risk 13) delivers a 404 for them until later features add pages, and verifies only `/dashboard` (TE-10). It is written down, so it is not a silent assumption, but it lives only in the risks list and is not a starred entry in the decision log. Consider making it a `D-` item so the gate confirmation is unmissable.
7. **INT-07 wording.** It says "the existing smoke test is known to fail until Phase 8" while listing `pnpm test`; the smoke test is Playwright (`pnpm test:e2e`) and is not part of `pnpm -r test`. Harmless, but the sentence is misleading.
8. **Fixture relocation at INT-01.** FE-12 places fixtures in `frontend/src/mocks/` and INT-01 relocates them to `frontend/src/test/`; component tests in Phase 8 reference the new path. This is consistent, but any colocated test written during Build (D-20) will import the old path and must be updated at INT-01; note this in INT-01's exit check.
