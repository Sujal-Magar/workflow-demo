## Verdict

**CHANGES REQUIRED**

The specs are sound. The plan and contract cover every FDS requirement, every behavior, and every acceptance criterion. The contract is complete and technology-agnostic. Three blocking problems remain, all in how the pieces connect:

1. The frontend's HTTP fetcher and its session layer import each other in a cycle, which the rules forbid. The plan also never says how the fetcher, which runs outside React, clears the session and redirects.
2. The Integration step will need to install a dependency, but the plan does not allow Integration to change the lockfile.
3. Several tasks have no tests, including environment validation. The 95% coverage gate counts every file under the three `src` trees, and the plan says nothing about how these files will be covered or excluded.

---

## Blocking Findings

### B-1 · Circular dependency, and no defined way for the fetcher to reach the session layer

- **Plan sections:** INT-02 (fetcher), INT-03 (`session-refresh.ts` import change), FE-10 (single-flight refresh, `clearSession`, redirect).
- **What the plan says:**
  - INT-02: the fetcher in `lib/api-client.ts` "triggers one single-flight refresh (FE-10)". If the refresh fails, the fetcher must "clear the session and redirect to `/auth`".
  - FE-10: the single-flight refresh lives in `features/auth/session/session-refresh.ts`. One of its callers is "the 401 retry", which is the fetcher.
  - INT-03: `session-refresh.ts` is switched to the real client, and `auth-api.ts` calls `lib/api-client.ts`.
- **Resulting import graph:** `lib/api-client.ts` → `session/session-refresh.ts` → `api/auth-api.ts` → `lib/api-client.ts`. That is a cycle.
- **Rules violated:**
  - `rules/architecture.md`, Forbidden Practices: "Do not create circular dependencies."
  - `rules/conventions.md`, Imports: "Avoid circular imports."
- **Second gap:** `clearSession` is a function on the React auth context (FE-10), and redirecting uses Next's `useRouter`, a React hook. The fetcher is module-level code outside React. The plan never says how the fetcher reaches either one.
- **Why it matters:**
  - FE-10 is built in Phase 5 without knowing how the fetcher will call it.
  - Integration (INT-02) would then have to design the mechanism itself, and possibly restructure FE-10, while being told "No business logic changes."
  - This path is REQ-AUTH-06 Renew and the client retry rule in contract §7. Both are core session behavior.
- **Spec:** REQ-AUTH-06 (Renew: "If the refresh fails, the session is cleared and the user is redirected to `/auth`"), contract §7 client retry rule.

### B-2 · `@ts-rest/core` is left to Integration, but Integration may not change the lockfile

- **Plan sections:** D-20, INT-02, §2 Execution Order (Integration row), D-01, S-01.
- **The conflict:**
  - D-20 adds `@ts-rest/core` to `frontend/package.json` "during Integration only if the custom fetcher's types are not re-exported by `@ts-rest/react-query`".
  - Adding a dependency changes `pnpm-lock.yaml`.
  - The §2 Integration row allows only `frontend/**`, `backend/**` (wiring only) and `playwright.config.ts`. It does not allow `pnpm-lock.yaml`.
  - D-01 says dependency installs happen only in S-01, which the developer runs by hand.
- **The condition in D-20 is already known:**
  - The installed `@ts-rest/react-query` 3.52.1 declares `@ts-rest/core ~3.52.0` as a required peer dependency.
  - Its v5 entry point re-exports only `types`, `init-tsr-react-query` and `type-guards`. It does not re-export `tsRestFetchApi` or `ApiFetcherArgs`, which a custom `api` fetcher normally imports.
  - `frontend/package.json` does not list `@ts-rest/core`, so pnpm's isolated `node_modules` will not let the frontend import it.
- **Result:** Integration will almost certainly hit this condition. It then either stops, or breaks its own path boundary.
- **Spec and rules:** `rules/tech-stack.md` API Contracts (`@ts-rest/core` is already approved); CLAUDE.md path boundaries; D-01 (from `directives.md` Revision 1, B-2).

### B-3 · Tasks with no tests, while the 95% gate counts every file

- **Plan sections:** BE-01, BE-02 (`db/client.ts`, `db/migrate.ts`), BE-14 (`index.ts`), FE-01 (`lib/env.ts`), FE-11 (`app/providers.tsx`, `app/layout.tsx`, `app/(protected)/layout.tsx`), FE-06 and FE-13 page wrappers (`app/auth/page.tsx`, `app/reset-password/page.tsx`), FE-14 (`app/(protected)/dashboard/page.tsx`); §8 Testing; TH-01 and TH-02.
- **Tasks with no test task at all:**
  - **BE-01** (validate `JWT_SECRET` has at least 32 characters; require `GOOGLE_CLIENT_ID` when `NODE_ENV=production`; apply the defaults). BE-01 is where D-08 is implemented. No test in §8.1 covers it.
  - **FE-01 `lib/env.ts`** (the D-19 `NEXT_PUBLIC_API_BASE_URL` fallback).
  - `rules/workflow.md` §2 Phase 8 and this review's checklist point 5 both say an implemented requirement with no test task is a finding.
- **Files that no test in §8 exercises:**
  - Backend: `backend/src/index.ts`, `backend/src/db/migrate.ts`, and the file-path branch of `db/client.ts` (creating the parent directory; all tests use `:memory:`).
  - Frontend: `app/layout.tsx` (uses `next/font/google`), `app/providers.tsx`, `app/auth/page.tsx`, `app/reset-password/page.tsx`, `app/(protected)/layout.tsx`, `app/(protected)/dashboard/page.tsx`.
- **The plan makes no exclusion decision for these files, and the gate will count them:**
  - `sonar.sources` covers all of `frontend/src`, `backend/src` and `packages/contracts/src`.
  - `sonar-project.properties` has no `sonar.coverage.exclusions`.
  - Vitest 2's v8 provider reports files that no test loaded as 0% covered (`coverage.all` is on by default).
  - TH-01 and TH-02 only set the reporters.
- **Why it matters:** with a 95% target (FDS frontmatter) and `compliance_relevant: true`, these files are a likely Phase 8c failure. Fixing that later means editing a root file, `sonar-project.properties`, which no agent in the plan is allowed to touch.
- **Spec:** FDS frontmatter `coverage_target: 95`; `rules/workflow.md` §2 Phase 8 (exit criteria), Phase 8c; REQ-AUTH-03 and D-08 (production audience requirement); FDS §3 (`Secure` flag from `NODE_ENV`).

## Advisory Findings

- **A-1 · Visual dimensions mix two scales (FE-06, FE-02).**
  - The reference PNGs are 2880 × 1912, a 2× capture of a 1440 × 956 viewport.
  - Two values in the plan are measured on a downscaled view of the PNG, not in CSS pixels: the card size "about 1110 × 830 px" and the input width "about 444".
  - Two other values are correct CSS pixels: the button's "about 160 × 40" and the input's "48" height.
  - In CSS pixels the card is about **800 × 600**, inputs about **320 × 48**, and buttons about **160 × 40**.
  - A 1110 px card holding 160 px buttons will look out of proportion. Phase 6 would catch this, but correcting the numbers now avoids a rework loop.
- **A-2 · `inert` in React 18 (FE-06).**
  - `@types/react` 18.3.31 has no `inert` prop.
  - React 18 also warns when a boolean is passed for an attribute it does not recognize.
  - With strict typing and no `any`, a Build agent could get stuck here. Say how to set it: through a ref (`element.inert = isHidden`, typed by `lib.dom`) or with the `inert=""` string pattern.
- **A-3 · Where the `/api/v1/auth` prefix lives in the typed contract (BE-03, BE-14, INT-02).**
  - INT-02 sets the client's base URL to the API origin only (`NEXT_PUBLIC_API_BASE_URL`). So the typed contract's paths must include `/api/v1/auth`, for example through a path prefix.
  - BE-14 says the "auth router under `/api/v1/auth`". Read literally, that could add the prefix a second time on the backend, or leave it out of the contract.
  - Add one line to BE-03 saying the typed contract carries the full path, and one to BE-14 saying the router is not mounted under an extra prefix.
- **A-4 · A `VALIDATION_ERROR` with no field that maps to the form gives no feedback (FE-04, FE-07, FE-08, FE-13).**
  - `apply-field-errors` ignores keys with no form field. A `VALIDATION_ERROR` with an empty `fieldErrors` (unparseable JSON) or only `token` would therefore show the user nothing.
  - The UI cannot trigger this today. Still, FE-04 should map it to "unexpected" so the FDS §5 Generic Failure Feedback applies, and T-UI-18 should test it.
- **A-5 · Forgot-password dialog close paths (T-UI-06).** behavior §6 step 1 requires the dialog to close on Escape, on an outside click, and through the close control. T-UI-06 tests only Escape. Add the other two.
- **A-6 · Other protected routes (D-13).**
  - REQ-AUTH-07 lists `/transactions`, `/budget`, `/goals`, `/reports` and `/profile` as redirecting to `/auth`.
  - Until their owning features exist, those URLs return 404, so Phase 9 Validation cannot verify that part.
  - D-13 records this but is not starred. Starring it would make the developer accept it explicitly at the gate.
- **A-7 · The dashboard's `/me` request is implied, not stated (FE-14, T-UI-14).**
  - T-UI-14 intercepts a `/me` call. That call only happens if the current-user query refetches on mount even though it has initial data, which is TanStack Query's default with `staleTime: 0`.
  - State this in FE-14 so a Build agent that sets a longer `staleTime` does not quietly remove the only real protected request.
- **A-8 · E2E Google configuration (INT-07, D-11).**
  - The backend loads the root `.env` (`index.ts`). A developer who added `GOOGLE_CLIENT_ID` there, as §3's "Developer action" suggests, will have it in E2E too.
  - Set it explicitly empty in the backend `webServer` env, and say in BE-01 that an empty value counts as unset.
  - Also, `reuseExistingServer: !process.env.CI` will reuse an already-running dev server that has the developer's own environment.
- **A-9 · Smoke-test update has no task ID or trace (§8.3).** The `e2e/smoke.spec.ts` change is real work that the UI/E2E agent must do. Give it an ID (for example T-UI-19) and trace it to REQ-AUTH-07 (root route).
- **A-10 · D-22 relies on an uncommitted prompt change.** The wider Unit/API scope that D-22 and TH-01 depend on is an uncommitted edit to `.ai/prompts/test-build-mode.md`. Commit it before the Approval Gate, so the frozen plan points to a scope that exists in the repository's history.

### B-1 options

- **A) Register handlers at runtime (recommended).**
  - How it works: `lib/api-client.ts` imports nothing from `features/auth/session/`. Instead it exports a small `registerSessionHandlers({ refreshSession, onSessionExpired })`. `AuthProvider` calls it on mount, passing its single-flight refresh and a function that clears the session and redirects to `/auth`. The fetcher calls whatever is registered.
  - Trade-off: the cycle is gone, and redirects stay in React. Before registration (the first render) the fetcher needs a sensible default, which is to return the 401 unchanged.
- **B) The API client owns the refresh.**
  - How it works: the single-flight refresh moves into `lib/api-client.ts`, which calls the refresh operation directly. The session layer imports it from there. The client tells the session layer about failure through a small listener (`onSessionExpired(listener)`) that `AuthProvider` subscribes to.
  - Trade-off: this is also cycle-free, with one clear owner of the token lifecycle. But FE-10's single-flight moves out of a Phase 5 frontend task, so Phase 5 would need to build it in `lib/`, and FE-10 and INT-02 must both change.
- **C) No refresh in the fetcher.**
  - How it works: the fetcher returns 401s unchanged. TanStack Query's error handlers (on the query cache and mutation cache) run the refresh and a manual retry.
  - Trade-off: no cycle, but the retry-once logic spreads across query and mutation handling. Retrying non-idempotent mutations exactly once is harder. The "one retry of the original request" rule in contract §7 is harder to guarantee and to test.

**Recommendation: A.** It is the smallest change: FE-10 keeps its single-flight, and INT-02 gains one registration step. It also works unchanged for the protected operations of every later feature.

### B-3 options

- **A) Test everything.**
  - Add unit tests for `backend/src/config/env.ts` and `frontend/src/lib/env.ts`.
  - Add render tests for `app/providers.tsx`, `app/layout.tsx` (mocking `next/font/google`), the `auth`, `reset-password` and `(protected)` pages and layout, plus a `db/client.ts` test on a temporary file path.
  - Refactor `backend/src/index.ts` so it can be imported without calling `listen`.
  - Trade-off: no exclusions, but tests for framework glue add little value, and it means refactoring the entry point.
- **B) Test the config modules, exclude thin entry points (recommended).**
  - Add unit tests for both `env.ts` modules, since they hold D-08, D-19 and the `JWT_SECRET` rule.
  - Add render tests for the route pages, layouts and `providers.tsx`, which hold guard and Suspense wiring.
  - Exclude only the process and framework entry points, which contain no rules: `backend/src/index.ts`, `backend/src/db/migrate.ts`, `frontend/src/app/layout.tsx`. Put the exclusions in `sonar.coverage.exclusions`, added by the developer in S-01, because it is a root file. Mirror them in `coverage.exclude` in TH-01 and TH-02, so local runs and Sonar report the same numbers.
  - Trade-off: a short, explicit exclusion list that must be written into the plan as a starred decision.
- **C) Lower or scope the target.**
  - Measure 95% only on `features/auth/**` and the contract's `auth/**`.
  - Trade-off: this changes how the FDS `coverage_target` is interpreted. That is a spec-level choice, and it is not recommended.

**Recommendation: B.**
