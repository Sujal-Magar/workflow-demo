# API Contract: profile (v1.0.0)

- **Feature:** `profile` (User Profile and Preferences)
- **FDS version:** 1.0.0 (`features/profile/fds.md`)
- **Produced by:** Plan Synthesizer, from `fragments/frontend.md` §5 and `fragments/backend.md` §5
- **Status:** Draft. Frozen at the Developer Approval Gate (Phase 4). After that, Frontend Build, Backend Build and Integration build against this file as written. Neither side may edit it.
- **Companion plan:** `plan.md` (same directory)

This document is the only source of truth for the Frontend/Backend interface of `profile`. It is plain language on purpose and does not assume any framework. Turning it into the project's typed contract package is a Backend Build task (see `plan.md`, task BE-02).

`profile` depends on `auth` (`features/index.json`). Every operation below reuses the authentication mechanism, `ErrorBody` shape, and error codes already defined in `features/auth/plans/v1.0.0/contract.md` (§2.5, §3, §9) rather than redefining them.

## 1. General Conventions

| Topic                              | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| :--------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Base path                          | Every operation is served under `/api/v1/profile`. Paths below are relative to it (for example `/change-password` means `/api/v1/profile/change-password`).                                                                                                                                                                                                                                                                                           |
| Body format                        | Request and response bodies are JSON (`Content-Type: application/json`), except `exportUserData`'s response (see §2.6). Operations marked "no body" ignore any body that is sent.                                                                                                                                                                                                                                                                     |
| Unknown / not-accepted body fields | Ignored. They never cause an error, are never applied, and are never echoed back. In particular, `preferredCurrency`, `language`, `monthlyStartDate`, `email`, `id`, `createdAt` and `updatedAt` sent on `updateUserProfile` are silently ignored (§7 C3) — REQ-PROF-02 keeps those three read-only in v1.0.0, and the other four are never writable through any `profile` endpoint.                                                                  |
| Auth                               | Every operation requires `Authorization: Bearer <accessToken>`, exactly as `features/auth/plans/v1.0.0/contract.md` §9 defines for every other feature's protected operations. A missing, malformed, invalid or expired token returns `401 UNAUTHENTICATED` with the shared `ErrorBody` shape, and participates in the auth contract's existing client retry rule (one `refreshSession` + one retry). This contract does not redefine that mechanism. |
| Scope                              | Every operation reads and writes only the data of the user identified by the access token. There is no cross-user access in this contract.                                                                                                                                                                                                                                                                                                            |
| Timestamps                         | `createdAt` / `updatedAt` on `UserProfile` are ISO-8601 UTC strings. No other timestamp appears.                                                                                                                                                                                                                                                                                                                                                      |
| Undeclared outcomes                | The client treats any status or `code` not declared for an operation (including network failure and any `5xx`) as "unexpected" and applies a generic failure message. The server never returns a `2xx` other than the one declared per operation.                                                                                                                                                                                                     |

## 2. Shared Shapes

### 2.1 `UserProfile` (fds.md §2)

| Field                     | Type                                             | Notes                                                                                                                                                                                                                                                                             |
| :------------------------ | :----------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                      | UUID string                                      | **Equal to the account's user id** (the same id already known to the frontend from `auth`'s `getCurrentUser` / `PublicUser.id`), not a separate internal surrogate key. There is exactly one profile per user, so this keeps profile identity consistent across features (§7 C1). |
| `name`                    | string                                           | 2–100 characters. Owned by the `auth` feature's `users` table; `profile` writes it through `updateUserProfile` (see plan BE-05).                                                                                                                                                  |
| `email`                   | string                                           | Always lowercase. Read-only through every `profile` endpoint (D-02).                                                                                                                                                                                                              |
| `avatarUrl`               | string \| `null`                                 | A URL. `null` when unset. See §2.3 and §7 C2 for why this is a plain string and not an uploaded file.                                                                                                                                                                             |
| `preferredCurrency`       | enum: `"NPR"` \| `"USD"` \| `"EUR"` \| `"GBP"`   | Read-only in v1.0.0 (REQ-PROF-02). Default `"NPR"`.                                                                                                                                                                                                                               |
| `language`                | enum: `"en_US"` \| `"en_GB"` \| `"es"` \| `"fr"` | Read-only in v1.0.0. Default `"en_US"`.                                                                                                                                                                                                                                           |
| `monthlyStartDate`        | integer                                          | 1–28. Read-only in v1.0.0. Default `1`.                                                                                                                                                                                                                                           |
| `notificationPreferences` | `NotificationPreferences` (§2.2)                 | Always all three keys present.                                                                                                                                                                                                                                                    |
| `createdAt`               | ISO timestamp string                             | Profile record creation.                                                                                                                                                                                                                                                          |
| `updatedAt`               | ISO timestamp string                             | Last update to any profile field.                                                                                                                                                                                                                                                 |

### 2.2 `NotificationPreferences`

| Field                 | Type    | Default |
| :-------------------- | :------ | :------ |
| `budgetLimitAlerts`   | boolean | `true`  |
| `goalReminders`       | boolean | `true`  |
| `weeklySummaryEmails` | boolean | `true`  |

### 2.3 `UpdateUserProfileRequest` (body of `updateUserProfile`)

| Field                     | Type             | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| :------------------------ | :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`                    | string, optional | When present: 2–100 characters, trimmed before checking and storing (same trimming convention as `features/auth/plans/v1.0.0/contract.md` §5). Absent = unchanged.                                                                                                                                                                                                                                                                                                  |
| `avatarUrl`               | string, optional | When present: a non-empty URL. Absent = unchanged. **When the Edit Profile dialog's Avatar URL field is empty, the client omits `avatarUrl` from the request body entirely (treated as unchanged); it never sends an empty string.** An explicit empty string, if ever sent, is rejected with `400 VALIDATION_ERROR` (`fieldErrors`: `avatarUrl`) rather than treated as "clear the avatar" — v1.0.0 has no clear-avatar affordance; the FDS does not describe one. |
| `notificationPreferences` | object, optional | Each of `budgetLimitAlerts`, `goalReminders`, `weeklySummaryEmails` is itself optional and boolean when present. Absent keys are unchanged. One PATCH serves both the "Edit Profile" dialog (`name` + `avatarUrl`) and a single notification toggle (one `notificationPreferences` key) — the FDS declares only one `updateUserProfile` operation (§7 C4).                                                                                                          |

At least one of `name`, `avatarUrl`, `notificationPreferences` must be present and non-empty, or the request is rejected with `400 VALIDATION_ERROR` (`fieldErrors` empty) — an empty-bodied PATCH has nothing to do.

### 2.4 `ChangePasswordRequest` (body of `changePassword`)

| Field             | Type   | Notes                                                                                                                                                                                                                                                                                                                                                                          |
| :---------------- | :----- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `currentPassword` | string | Required, non-empty.                                                                                                                                                                                                                                                                                                                                                           |
| `newPassword`     | string | Required. Complexity: at least 8 characters, at least one digit, at least one special (non-alphanumeric) character — the same `StrongPassword` rule set `auth` already defines (`features/auth/plans/v1.0.0/contract.md` §5), reused rather than redefined (§7 C5).                                                                                                            |
| `confirmPassword` | string | Required, non-empty. Whether it equals `newPassword` is **not** checked by this rule set — that check is its own error code, `PASSWORDS_DO_NOT_MATCH` (§3), evaluated after the fields below pass basic validation (unlike `auth`'s generic confirm-password mismatch, which reports under `VALIDATION_ERROR`; see §7 C6 for why `profile` does not reuse that behavior here). |

### 2.5 `ProfileSuccessAck` (body of `changePassword` and `clearAllUserData` on success)

| Field     | Type    | Notes                                                                                                                         |
| :-------- | :------ | :---------------------------------------------------------------------------------------------------------------------------- |
| `success` | boolean | Always `true`                                                                                                                 |
| `message` | string  | Fixed per operation (§6.3, §6.5). Informational only; the UI shows its own copy from `behavior.md` (§7 C7), never this field. |

### 2.6 `exportUserData` response body

Identical field set to `UserProfile` (§2.1) — `id`, `name`, `email`, `avatarUrl`, `preferredCurrency`, `language`, `monthlyStartDate`, `notificationPreferences`, `createdAt`, `updatedAt` — serialized as JSON. Per developer directive D-01, this payload contains **only** profile-owned fields; it has no `transactions`, `budgets` or `goals` keys in v1.0.0, because those tables do not exist yet. Served with `Content-Type: application/json` and `Content-Disposition: attachment; filename="profile-export-<ISO-date>.json"` so the browser downloads it directly from the one request (§7 C8).

### 2.7 `ClearAllUserDataRequest` (body of `clearAllUserData`)

| Field          | Type            | Notes                                                                                                                  |
| :------------- | :-------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `confirmation` | string, literal | Must be exactly `"DELETE"`. Any other value (including absent, empty, or differently-cased) is `400 VALIDATION_ERROR`. |

## 3. Error Code Catalog (profile-specific additions)

`profile` reuses `VALIDATION_ERROR` (400), `UNAUTHENTICATED` (401), `NOT_FOUND` (404) and `INTERNAL_ERROR` (500) from the shared catalog (`features/auth/plans/v1.0.0/contract.md` §3) with the same fixed messages and meanings. It adds four codes, all required by `fds.md` §5's error table:

| Code                     | Status | Fixed `message`                                                       | Meaning                                                                                                                                                                                                                                                    |
| :----------------------- | :----- | :-------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PASSWORD_NOT_SET`       | 400    | `No password is set for this account. Use password recovery instead.` | The account has `passwordHash = null` (Google SSO, never set a password). Not counted as a rate-limit failure.                                                                                                                                             |
| `SAME_PASSWORD`          | 400    | `New password must be different from your current password.`          | `newPassword` equals the already-verified `currentPassword`.                                                                                                                                                                                               |
| `PASSWORDS_DO_NOT_MATCH` | 400    | `New password and confirmation do not match.`                         | `confirmPassword` does not equal `newPassword`.                                                                                                                                                                                                            |
| `RATE_LIMIT_EXCEEDED`    | 429    | `Too many password change attempts. Please try again later.`          | 5 or more failed `currentPassword` checks for this user within a rolling 15-minute window. The window's start boundary is **exclusive** (D-17): a failed attempt recorded exactly 15 minutes before the current one no longer counts toward the threshold. |

All four are added to the shared contract package's `ERROR_CODES` / `ERROR_MESSAGES` catalog (`packages/contracts/src/common/error-body.ts`) and to `backend/src/shared/errors/error-handler.ts`'s `ERROR_STATUS`, alongside the existing auth codes — not a parallel catalog (plan BE-03).

Every operation below may also return `500 INTERNAL_ERROR` and `401 UNAUTHENTICATED`; neither is repeated per operation.

## 4. Shared Validation Rule Sets

| Rule set                  | Field(s)          | Rules in order → message                                                                                                                                                                                                                                                                                                                |
| :------------------------ | :---------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DisplayName`             | `name`            | 1. empty (after trim) → `Name is required.` 2. fewer than 2 characters → `Name must be at least 2 characters.` 3. more than 100 characters → `Name must be at most 100 characters.`                                                                                                                                                     |
| `AvatarUrl`               | `avatarUrl`       | 1. present and empty string → `Avatar URL cannot be empty.` (absence is fine; emptiness is not — §2.3)                                                                                                                                                                                                                                  |
| `CurrentPassword`         | `currentPassword` | 1. empty → `Current password is required.`                                                                                                                                                                                                                                                                                              |
| `NewStrongPassword`       | `newPassword`     | Reused verbatim from `auth`'s `StrongPassword` rule set (`features/auth/plans/v1.0.0/contract.md` §5): 1. empty → `Password is required.` 2. fewer than 8 characters → `Password must be at least 8 characters.` 3. no digit → `Password must include a number.` 4. no special character → `Password must include a special character.` |
| `ConfirmPasswordPresence` | `confirmPassword` | 1. empty → `Please confirm your password.` (the _match_ check is a separate, later step — §2.4, §7 C6, not part of this rule set)                                                                                                                                                                                                       |
| `ClearDataConfirmation`   | `confirmation`    | 1. not exactly `"DELETE"` → `Type DELETE to confirm.`                                                                                                                                                                                                                                                                                   |

`DisplayName` is **not** the same rule set as `auth`'s `Name` (which has no upper bound) — `fds.md` §4 gives `profile`'s `name` field an explicit 100-character ceiling that `auth`'s `name` field does not have, so reusing `auth`'s schema outright would silently drop that bound (§7 C9). Normalization: `name` is trimmed before checking and storing, exactly as `auth` already does for its own `name` field.

**Composed request rule sets:**

| Composed set               | Fields → rule set                                                                                                                                    | Used by                                                                                                                                   |
| :------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------- |
| `UpdateUserProfileRequest` | `name` → `DisplayName` (only if present); `avatarUrl` → `AvatarUrl` (only if present); each present `notificationPreferences.*` → boolean type check | `updateUserProfile`                                                                                                                       |
| `ChangePasswordRequest`    | `currentPassword` → `CurrentPassword`; `newPassword` → `NewStrongPassword`; `confirmPassword` → `ConfirmPasswordPresence`                            | `changePassword` (contract/Zod layer only — `SAME_PASSWORD` and `PASSWORDS_DO_NOT_MATCH` are service-layer checks, run after this passes) |
| `ClearAllUserDataRequest`  | `confirmation` → `ClearDataConfirmation`                                                                                                             | `clearAllUserData`                                                                                                                        |

## 5. Operations

### 5.1 `getUserProfile` — read the caller's full profile

| Item          | Value                                                                                                                                                                                                                                                 |
| :------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Method & path | `GET /` (i.e. `GET /api/v1/profile`)                                                                                                                                                                                                                  |
| Auth          | Bearer                                                                                                                                                                                                                                                |
| Request       | No body                                                                                                                                                                                                                                               |
| Success       | `200`, body `UserProfile` (§2.1)                                                                                                                                                                                                                      |
| Side effects  | None visible to the client. (A profile row is lazily created with baseline defaults on first access for any user who has none — an internal implementation detail that never changes this operation's declared shape or status; see `plan.md` BE-06.) |

No declared errors beyond `401 UNAUTHENTICATED`.

### 5.2 `updateUserProfile` — edit display name, avatar, and/or notification toggles

| Item          | Value                                          |
| :------------ | :--------------------------------------------- |
| Method & path | `PATCH /`                                      |
| Auth          | Bearer                                         |
| Request body  | `UpdateUserProfileRequest` (§2.3)              |
| Success       | `200`, body the refreshed `UserProfile` (§2.1) |

| Status | `code`             | When                                                                                    | `fieldErrors` keys                                                                                                                                              |
| :----- | :----------------- | :-------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `VALIDATION_ERROR` | Body fails `UpdateUserProfileRequest` (§4), is not valid JSON, or every field is absent | any of `name`, `avatarUrl`, `notificationPreferences.budgetLimitAlerts`, `notificationPreferences.goalReminders`, `notificationPreferences.weeklySummaryEmails` |

### 5.3 `changePassword` — update the caller's login password

| Item          | Value                                                                                                                                                                                                                                                                      |
| :------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Method & path | `POST /change-password`                                                                                                                                                                                                                                                    |
| Auth          | Bearer                                                                                                                                                                                                                                                                     |
| Request body  | `ChangePasswordRequest` (§2.4)                                                                                                                                                                                                                                             |
| Success       | `200`, body `ProfileSuccessAck` (§2.5), `message` = `Password updated successfully.`                                                                                                                                                                                       |
| Side effects  | `users.passwordHash` updated; **every** refresh token for the user is revoked (the client's own session is expected to re-authenticate on its next refresh, same as `auth`'s `resetPassword`). A failed `currentPassword` check records one attempt toward the rate limit. |

Checks run in this order (service layer, authoritative):

1. Rate limit: 5+ recorded failures in the last 15 minutes → `429 RATE_LIMIT_EXCEEDED`.
2. Account state: `passwordHash === null` → `400 PASSWORD_NOT_SET` (not recorded as a rate-limit failure).
3. Credential check: `currentPassword` wrong → `401 INVALID_CREDENTIALS` (recorded as a failure).
4. Same-password check: `newPassword === currentPassword` → `400 SAME_PASSWORD`.
5. Confirmation match: `confirmPassword !== newPassword` → `400 PASSWORDS_DO_NOT_MATCH`.

| Status | `code`                   | When                                                         | `fieldErrors` keys                                  |
| :----- | :----------------------- | :----------------------------------------------------------- | :-------------------------------------------------- |
| 400    | `VALIDATION_ERROR`       | Body fails `ChangePasswordRequest` (§4) or is not valid JSON | `currentPassword`, `newPassword`, `confirmPassword` |
| 400    | `PASSWORD_NOT_SET`       | Account has no password (step 2)                             | —                                                   |
| 400    | `SAME_PASSWORD`          | `newPassword` equals `currentPassword` (step 4)              | —                                                   |
| 400    | `PASSWORDS_DO_NOT_MATCH` | `confirmPassword` ≠ `newPassword` (step 5)                   | —                                                   |
| 401    | `INVALID_CREDENTIALS`    | `currentPassword` is wrong (step 3)                          | —                                                   |
| 429    | `RATE_LIMIT_EXCEEDED`    | 5+ failures in 15 minutes (step 1)                           | —                                                   |

### 5.4 `exportUserData` — download the caller's profile-owned data (D-01 scope)

| Item          | Value                                                   |
| :------------ | :------------------------------------------------------ |
| Method & path | `GET /export`                                           |
| Auth          | Bearer                                                  |
| Request       | No body                                                 |
| Success       | `200`, body per §2.6, `Content-Disposition: attachment` |

No declared errors beyond `401 UNAUTHENTICATED`.

### 5.5 `clearAllUserData` — reset profile configuration to baseline (D-01 scope)

| Item          | Value                                                                                                                                                                                                                                                                                                                                                                                           |
| :------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Method & path | `POST /clear-data`                                                                                                                                                                                                                                                                                                                                                                              |
| Auth          | Bearer                                                                                                                                                                                                                                                                                                                                                                                          |
| Request body  | `ClearAllUserDataRequest` (§2.7)                                                                                                                                                                                                                                                                                                                                                                |
| Success       | `200`, body `ProfileSuccessAck` (§2.5), `message` = `All profile data has been cleared.`                                                                                                                                                                                                                                                                                                        |
| Side effects  | `avatarUrl`, `notificationPreferences.*` reset to baseline defaults (`null`, `true`/`true`/`true`); `preferredCurrency`/`language`/`monthlyStartDate` reset to defaults (`"NPR"`/`"en_US"`/`1`). Per D-01, **does not** touch `users` (`name`, `email`, `passwordHash` untouched) and **does not** touch any `transactions`/`budget`/`goals` data, because those tables do not exist in v1.0.0. |

| Status | `code`             | When                                                                | `fieldErrors` keys |
| :----- | :----------------- | :------------------------------------------------------------------ | :----------------- |
| 400    | `VALIDATION_ERROR` | `confirmation` is not exactly `"DELETE"`, or body is not valid JSON | `confirmation`     |
