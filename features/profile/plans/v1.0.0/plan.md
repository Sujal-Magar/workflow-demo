# Implementation Plan: profile (v1.0.0)

- **Feature:** `profile`, User Profile and Preferences
- **FDS version:** 1.0.0 (`features/profile/fds.md`, changelog entry 1.0.0 dated 2026-10-01)
- **Scenario:** New Standalone Feature. `fds.md` changelog has a single entry, so this plan covers the whole FDS. `profile` is listed as a dependency of `auth` (`features/index.json`), but `auth` is already built and frozen, and neither fragment needs to change any existing `auth` behavior — only to add one new, additive repository method (BE-04) and reuse existing auth ports/repositories (BE-06, BE-07). This does **not** meet the Cross-Feature Dependency scenario's bar for a 2-phase Foundation-Refactoring plan (`rules/workflow.md` §2 Phase 1, `.ai/prompts/plan/plan-synthesizer.md` Scenario Handling): directive D-01 already confirms the alternative (inverting `features/index.json` so `transactions`/`budget`/`goals` precede `profile`) was considered and rejected.
- **Complexity:** spec stability 1 (two ambiguity rounds already resolved via `directives.md`, plus one further ambiguity resolved during this synthesis — see `contract.md` §7 C2) + UI/API surface 2 (multi-component page, new API contract) + team/agent separation 2 (dedicated frontend + backend fragments) = **5**, so the full Multi-Agent pipeline applies (`rules/workflow.md` §5).
- **Coverage target:** 85% (`fds.md` frontmatter). `compliance_relevant: true`, so the Validation Report is persistent.
- **Sources synthesized:** `fragments/frontend.md`, `fragments/backend.md`, `fds.md`, `behavior.md`, `visuals/profile-page.png`, `directives.md` (D-01, D-02, D-16, D-17, D-18), `rules/*`, `features/index.json`, and the already-frozen `features/auth/plans/v1.0.0/plan.md` / `contract.md` for the ports, repositories and conventions `profile` reuses. Revision round 1 (`review.md` CHANGES REQUIRED, B-1, B-2): applied D-16 and the round-1 B-1 fix. Revision round 2 (`review.md` CHANGES REQUIRED, B-1, B-2): rewrote `BE-10` so `ProfilePersistence`/`ProfileService` are constructed and the profile router mounted inside `createApp()` (`backend/src/app.ts`), not `index.ts` (B-1); applied D-17's exclusive rate-limit window boundary to `BE-05`, `BE-07`, `T-UA-02`, and `contract.md` §3 (B-2). Revision round 3 (`review.md` CHANGES REQUIRED, B-1, B-2): applied D-18 to `FE-07`, Decision Log D-18, and Spec Traceability Matrix. Revision round 4 (`review.md` CHANGES REQUIRED, B-1): developer authorized proceeding past retry bound (`rules/workflow.md` §8); resolved B-1 by correcting `T-UI-07` toast text to `"All profile data has been cleared."`.
- **API Contract:** [`contract.md`](contract.md) in this directory. It is the only definition of routes, bodies, statuses and error codes. This plan refers to it and does not repeat it.

**How to read task entries.** Each task has an ID, a `layer` (which build session owns it), the files it creates or changes, what "done" means, and its spec trace. Paths are relative to the repository root. Build agents implement tasks in ID order within their layer unless a task says otherwise.

## 3. Backend Section (`layer: backend`, paths `backend/` and `packages/contracts/`)

Layering follows `rules/architecture.md`: Presentation (router) calls `ProfileService` only; the service holds every business rule and never sees `req`/`res`; repositories are the only code that touches Drizzle. `ProfileService` is constructed with `profilePersistence: ProfilePersistence`, `authPersistence: AuthPersistence` (existing, reused), `passwordHasher: PasswordHasher` (existing port, reused), `clock: Clock` (existing, reused) — no new ports are needed.

**Named constants** (one module, `backend/src/features/profile/profile-constants.ts`): rate-limit window 15 min, rate-limit threshold 5 failures, password-changed message, data-cleared message, export filename pattern.

### BE-01 · Data model / Drizzle schema

- **Files:** `backend/src/db/schema/profile.ts` (new), `backend/src/db/schema/index.ts` (add `export * from "./profile"`).
- `user_profiles` (one row per user): `id` (text PK, UUID), `user_id` (text NOT NULL, FK → `users.id`, UNIQUE, cascade on delete), `avatar_url` (text, nullable), `preferred_currency` (text enum `NPR`/`USD`/`EUR`/`GBP`, default `"NPR"`), `language` (text enum `en_US`/`en_GB`/`es`/`fr`, default `"en_US"`), `monthly_start_date` (integer, default `1`, hand-added `CHECK (1 <= monthly_start_date AND monthly_start_date <= 28)` on the generated migration, same drizzle-kit limitation and pattern as `auth`'s `users` CHECK constraint), `notification_budget_limit_alerts` / `notification_goal_reminders` / `notification_weekly_summary_emails` (integer-as-boolean, default `1`), `created_at`, `updated_at` (text ISO timestamps). Index `user_profiles_user_id_idx` on `user_id`.
- `password_change_attempts` (rate-limit ledger): `id` (text PK), `user_id` (text NOT NULL, FK → `users.id`, cascade), `attempted_at` (text ISO timestamp, recorded only for failed credential checks). Index `password_change_attempts_user_id_idx` on `(user_id, attempted_at)`.
- No existing table (`users`, `refresh_tokens`, `password_reset_tokens`) is modified.
- **Done when:** the generated migration applies cleanly to a fresh `:memory:` database and to the existing `data/app.db` schema. Tests: T-UA-01, T-UA-02.
- **Trace:** `fds.md` §2 (`UserProfile` data model); `fds.md` §4 (`monthlyStartDate` 1–28); D-01; `rules/architecture.md` Database.

### BE-05 · Repository layer

- **Files:** `backend/src/features/profile/profile-repository.ts`, `backend/src/features/profile/password-change-attempt-repository.ts`, `backend/src/features/profile/profile-persistence.ts`.
- `ProfileRepository`: `findByUserId(userId): ProfileRecord | null`; `create(newProfile): ProfileRecord` (inserts the baseline-default row); `update(userId, patch): ProfileRecord` (partial update of `avatarUrl` / notification flags only — never `preferredCurrency`/`language`/`monthlyStartDate`); `resetToDefaults(userId, updatedAt): ProfileRecord` (same baseline values as `create`, keeps the same row, so `id`/`createdAt` are preserved).
- `PasswordChangeAttemptRepository`: `recordFailure(userId, attemptedAt): void`; `countFailuresSince(userId, since): number` — counts rows where `attempted_at > since`, strictly greater than (exclusive boundary, D-17): a row with `attempted_at` exactly equal to `since` is not counted.
- `ProfilePersistence`: unit of work exposing `profiles` and `passwordChangeAttempts` repositories plus `runInTransaction`, mirroring `AuthPersistence`'s shape exactly.
- Repositories contain no business rules; all Drizzle access stays inside them (`rules/architecture.md` Repository Layer).
- **Done when:** every method above exists and is covered. Tests: T-UA-01, T-UA-02.
- **Trace:** `fds.md` §2; `rules/architecture.md` Repository Layer, Transactions; D-17.

### BE-06 · `ProfileService.getProfile` and `updateProfile`

- **Files:** `backend/src/features/profile/profile-service.ts` (new).
- **`getProfile(userId): UserProfile`:** `getOrCreateProfile(userId)` (D-11: look up by `userId`; if absent, insert baseline defaults) via `profilePersistence.profiles`. Reads `name`/`email` via `authPersistence.users.findById(userId)` (the caller is already authenticated). Assembles the full `UserProfile` (D-04: `id` = user id).
- **`updateProfile(userId, input): UserProfile`:** `input` has optional `name`, `avatarUrl`, `notificationPreferences.*` (D-06). `name`, when provided, writes to `authPersistence.users.updateName(...)` (BE-04). `avatarUrl`, when provided, writes to `user_profiles.avatar_url` (rejects an explicit empty string, contract §2.3). `notificationPreferences.*`, when provided, writes the corresponding boolean column. `preferredCurrency`/`language`/`monthlyStartDate` are never read from `input` even if present (D-05). Returns the refreshed `UserProfile` (same assembly as `getProfile`).
- **Done when:** both methods behave per `contract.md` §5.1–§5.2. Tests: T-UA-03, T-UA-04.
- **Trace:** REQ-PROF-01, REQ-PROF-02; `fds.md` §4 (name length); `contract.md` §5.1, §5.2; D-04, D-05, D-06, D-11, D-12.

### BE-07 · `ProfileService.changePassword`

- **Files:** `profile-service.ts` (method).
- Implements the five-step order in `contract.md` §5.3 exactly: (1) rate limit via `passwordChangeAttempts.countFailuresSince(userId, now - 15min)` — per D-17 the window's start boundary is exclusive, so a failure recorded exactly 15 minutes ago no longer counts — `>= 5` → `RateLimitExceededError`; (2) `authPersistence.users.findById(userId)`, `passwordHash === null` → `PasswordNotSetError` (not recorded as a failure); (3) `passwordHasher.verify(...)`, invalid → record failure, then `InvalidCredentialsError` (reused from `auth-errors.ts`); (4) `newPassword === currentPassword` → `SamePasswordError`; (5) `confirmPassword !== newPassword` → `PasswordsDoNotMatchError`; (6) persist: hash `newPassword`, then in one transaction via `authPersistence.runInTransaction(...)`, `repos.users.updatePasswordHash(...)` and `repos.refreshTokens.revokeAllForUser(...)` (both existing, unchanged `auth` methods).
- **Done when:** the full rule matrix in `contract.md` §5.3 passes. Tests: T-UA-05.
- **Trace:** `fds.md` §4 Change Password Validation & Security Rules; `contract.md` §5.3; D-07, D-17.
