## Verdict: CHANGES REQUIRED

## Blocking Findings

### B-1 — `avatarUrl` handling on `updateUserProfile` is unspecified for the "no avatar yet" case

- **Plan section / spec conflict:** `plan.md` FE-04 (Edit Profile dialog) and `contract.md` §2.3 (`UpdateUserProfileRequest`), against `fds.md` §6 Acceptance Criteria ("User can update display name and avatar via the 'Edit Profile' dialog ... with immediate UI reflection") and `behavior.md` §2 ("Saving updates values immediately").
- **Severity condition:**
  - **(e) Contract gap.** `contract.md` §2.3 states an explicit empty-string `avatarUrl` is rejected with `400 VALIDATION_ERROR` ("v1.0.0 has no clear-avatar affordance"), but never states what the Edit Profile dialog must send when its Avatar URL field is blank. Frontend Build and Backend Build implement this contract in parallel without seeing each other's work (`plan.md` §2, `contract.md` header); this exact seam is the one the contract exists to close, and it is open here.
  - **(c) Not executable.** FE-04 only says the field has "a live preview," not what happens to an empty value on submit. An agent implementing FE-04 has to invent the serialization rule itself.
- **Concrete failure:** Per D-11, every profile is lazily created with `avatarUrl: null`. The most natural implementation — a controlled text input defaulting to `""` — will submit `avatarUrl: ""` whenever a user who has never set an avatar edits only their display name. Per `contract.md` §2.3 that is a `400 VALIDATION_ERROR` on every such save, breaking the "immediate UI reflection" acceptance criterion for what will be the single most common Edit Profile interaction (a brand-new account). `T-UI-03` does not cover this path either, so Phase 8 would not catch it until the behavior is already built.
- **Origin:** Pre-existing (first review of this plan version; no earlier revision exists).

### B-2 — `behavior.md` §1's navigation entry point has no implementing task, no test, and D-13 is unstarred

- **Plan section / spec conflict:** `plan.md` Decision Log D-13, against `behavior.md` §1 ("Clicking the User Profile avatar icon in the top right of the navigation header navigates to `/profile`.").
- **Severity condition:** **(a) Spec violation.** A `behavior.md`-described interaction has no implementing task and no verifying test anywhere in the plan. `plan.md` §7's Spec Traceability Matrix never cites `behavior.md` §1's navigation bullet as covered by anything other than D-13 declaring it out of scope — the requirement is not merely untested, it is explicitly excluded.
- **Why D-13 doesn't settle this on its own:** D-13 is correct that no shared nav component exists yet (confirmed: `frontend/src/app/(protected)/layout.tsx` only wraps children in `ProtectedRoute`, no header). But D-13 is not starred, even though it is a genuine two-option choice the Plan Synthesizer made unilaterally — it is not dictated by `fds.md`/`behavior.md` the way an unstarred entry should be, and it was not routed through `directives.md` for developer sign-off. Nothing in `fds.md` or `behavior.md` marks this item as deferred the way REQ-PROF-02's currency/language/date editing is explicitly marked "deferred to v1.1.0." Per `rules/workflow.md` §4, a gap "always implied by the FDS, just not written explicitly" is a Clarification requiring only an in-place addendum — but no such addendum exists, so as written the plan silently drops a `behavior.md` requirement rather than clarifying it.
- **Origin:** Pre-existing.

## Advisory Findings

- **A-1 (Decision Log gap, symmetry with D-15):** `fds.md` §4 describes the Clear All Data confirmation as "explicit confirmation string input (e.g., typing 'DELETE' or confirming via modal dialog)" — two different mechanisms offered as examples. `contract.md` §2.7 / `plan.md` FE-07 pick the stricter one (typed `"DELETE"`) without a Decision Log entry, unlike the directly comparable D-15 (export format, "fds.md allows either, chosen X"). Recommend adding a starred entry for explicit developer confirmation, since `behavior.md` §5 doesn't mention typing a string either.
- **A-2 (Decision Log gap):** Per `contract.md` §5.3, only a wrong `currentPassword` counts toward the 5-failure rate limit; `SAME_PASSWORD`, `PASSWORDS_DO_NOT_MATCH` and body-validation failures do not. `fds.md` §4 just says "5 failed attempts" without specifying which failures count. The chosen scope (credential-guessing only) is the conventional, defensible reading, but it is an interpretation, not a stated rule, and isn't recorded.
- **A-3 (directive application, not reopening D-01):** Per D-01, `clearAllUserData` also resets `avatarUrl` and `notificationPreferences` to baseline, not only `preferredCurrency`/`language`/`monthlyStartDate`. This is a defensible reading of D-01's "profile-level configurations/preferences," but `fds.md` REQ-PROF-04's own framing ("Preserves the base user profile account while resetting ledger datasets to zero") could be read as expecting personal preferences to survive a ledger wipe. Worth one explicit line of developer confirmation at the Approval Gate — not a reopening of D-01 itself.
- **A-4:** `UpdateUserProfileRequest`'s `fieldErrors` keys for notification toggles use a dotted path (`notificationPreferences.budgetLimitAlerts`), a convention not present in the auth `ErrorBody` this feature reuses (whose documented keys are always flat: `name`, `email`, ...). The shared schema (`z.record(z.string(), z.string())`) accepts it, but `contract.md` §2.5/§3 should say so explicitly, since other features will also reuse `ErrorBody`.
- **A-5:** `getOrCreateProfile` (D-11) has no stated behavior for two concurrent first-access requests racing on the `user_profiles.user_id` UNIQUE constraint. Low likelihood, not covered by a task or test.
