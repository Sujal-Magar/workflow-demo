## Blocking Findings

### B-1 — `BE-10` wires the new service in the wrong file; the profile router can never be reached by the test harness or `pnpm dev`

- **Plan section:** `plan.md` §3, task `BE-10` ("App wiring"): _"Files: `backend/src/app.ts` (register the profile router), `backend/src/index.ts` (construct `ProfilePersistence` and `ProfileService` with the real `PasswordHasher`/`Clock` adapters already wired for `auth`)."_
- **Conflicts with:** the actual, established pattern in `backend/src/app.ts`'s `createApp()`. Every piece of `auth`'s wiring — `AuthPersistence`, `Argon2PasswordHasher`, `JoseAccessTokenSigner`, `AuthService`, `PasswordResetService`, and the router mount itself — is constructed **inside** `createApp()`, from the generic dependencies (`config`, `db`, `clock`, `mailer`, `googleTokenVerifier`) already passed into it. `backend/src/index.ts` never constructs a feature's persistence or service; it only supplies those generic dependencies and calls `createApp(...)`. There is no sense in which "`PasswordHasher`/`Clock` adapters" are "already wired for `auth`" inside `index.ts` — they are wired inside `app.ts`, and `index.ts` is never imported by any test.
- **Severity condition:**
  - **(c) Not executable.** An agent following `BE-10` literally would construct `ProfilePersistence`/`ProfileService` in `index.ts`, a module `createApp()` never calls into and that no test imports. To make the profile router reachable at all, `AppDependencies`/`createApp()` would need an interface change `BE-10` never mentions — a decision the task leaves open that also affects Testing (Phase 8).
  - **(d) Gate cannot pass.** `backend/src/test-support/auth-test-harness.ts`'s `startTestApp()` — the harness `T-UA-09` is explicitly told to extend ("API/route level (extend `startTestApp`-style harness)") — builds the app exclusively via `createApp()`. If `ProfileService` and the profile router are wired from `index.ts` instead of inside `createApp()`, the profile router is never mounted on the app `startTestApp()` returns, so `T-UA-09`'s route-level tests have nothing to hit at `/api/v1/profile/*`. Phase 8's exit criterion ("All tests pass") cannot be met for this task as planned, and `BE-09`'s own done-criterion ("every route matches `contract.md` §5 exactly") can't be verified either.
- **Origin:** Pre-existing (not part of revision round 1 per `activity-log.md`'s entry for that round, and not named in `directives.md`'s D-16 "Apply to" list).

### B-2 — The password-change rate-limit window's boundary is decided only inside a test description, never as a written plan decision

- **Plan section:** `plan.md` §6.1, task `T-UA-02`: _"only counts within the rolling 15-minute window (`TestClock.advanceBy`); **boundary case at exactly 15 minutes is excluded**."_ Also `BE-07` ("rate limit via `passwordChangeAttempts.countFailuresSince(userId, now - 15min)`, `>= 5` → `RateLimitExceededError`") and `contract.md` §3 (`RATE_LIMIT_EXCEEDED`: _"5 or more failed `currentPassword` checks for this user within a rolling 15-minute window"_) — neither states whether an attempt exactly 15 minutes old counts.
- **Source text:** `fds.md` §4: _"Password change submissions are rate-limited to a maximum of 5 failed attempts per rolling 15-minute window per user."_ This does not say whether the window's start boundary is inclusive or exclusive, and "exactly excluded" is one of two equally defensible readings, not the only one a reasonable implementer would pick.
- **Severity condition:** **(f) Silent ambiguity.** The choice is pure assumption and it changes real, observable, security-relevant behavior: whether a user whose oldest counted failure is exactly 15:00:00 old is still rate-limited on the next attempt differs between the two readings, and the FDS text doesn't dictate one. It is also never written down anywhere decisions live — not `plan.md` §1's Decision Log (D-01…D-15 do not cover it), not `contract.md` §3's code definition, not `contract.md` §7's Conflict Resolutions. It surfaces for the first time inside a test's "Covers" cell, which is exactly the "ambiguity resolved by silent assumption" the single most important checklist point exists to catch.
- **Origin:** Pre-existing (not part of revision round 1).

## Advisory Findings

- **`D-15` (export format, JSON vs. CSV) is unstarred despite being a real either-way choice.** `fds.md` REQ-PROF-03 explicitly allows "JSON or CSV archive." The Plan Synthesizer picked JSON with a reasonable rationale, but this is the kind of choice the Decision Log's own rule ("★ = the developer should confirm this explicitly... It is a real choice, not something the specs dictate") describes — unlike, say, D-04 or D-11, which really do follow from the specs. Doesn't change any acceptance criterion's observable pass/fail, so it isn't Blocking, but the developer may want to confirm it explicitly at the Approval Gate rather than discover the format choice later.
- **`contract.md` §5.2 promises `fieldErrors` keys the existing shared validation-error helper cannot produce without a change.** The row for `updateUserProfile`'s `400 VALIDATION_ERROR` lists `fieldErrors` keys `notificationPreferences.budgetLimitAlerts`, `notificationPreferences.goalReminders`, `notificationPreferences.weeklySummaryEmails` (dotted, nested paths). The shared helper both `BE-02`/`BE-09` would reuse unchanged (`backend/src/shared/http/validation-error.ts`'s `toFieldErrors`) keys its output off `issue.path[0]` only — the top-level field name — so a nested Zod issue on `notificationPreferences.budgetLimitAlerts` would actually surface as `{ notificationPreferences: "<message>" }`, not the dotted key the contract documents. No task in the plan touches this helper or flags the gap. In practice nothing currently consumes the dotted key (`FE-06`'s notification toggles only react to success/failure generically with a toast, and `FE-04` never sends `notificationPreferences`), so this doesn't change any built behavior today — that's why it's Advisory, not Blocking — but it's worth a conscious decision (either fix the contract's documented shape or extend the helper) before a future version adds a UI that does read these keys.
- **`contract.md` §2.6's "the browser downloads it directly from the one request" undersells what `FE-07`/`FE-08` actually have to build.** `rules/architecture.md` requires all API communication through the ts-rest/TanStack Query client, which consumes the response as parsed JSON in JS, not as a browser-level navigation — a `Content-Disposition: attachment` header alone will not pop a native download dialog through `fetch`. Build still needs the standard Blob + `URL.createObjectURL` + synthetic-anchor-click technique to actually trigger a save. This is a well-known, single-answer technique (not an ambiguous choice), so it doesn't meet a Blocking condition, but the contract's phrasing reads as if the header alone suffices.
- **`plan.md` §4's framing note ("mirroring the `features/auth/` layout (`api/`, `components/`, `hooks/`, `lib/`, `mocks/`)") cites a `mocks/` directory that doesn't currently exist under `frontend/src/features/auth/`.** Cosmetic only — `FE-09`/`INT-02` already plan to create and then delete `profile`'s own mocks, so this doesn't change any task's outcome.
