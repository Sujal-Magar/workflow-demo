## Blocking Findings

### B-1 — "Clear All Data" promises deletion of data it will never touch (REQ-PROF-04)

- **Origin:** Pre-existing. Neither revision round touched `behavior.md` §4/§5, `fds.md` §3/§6, or the `FE-07`/`BE-08` task text — round 1 touched `behavior.md` §1 (D-16) and round 2 touched `BE-05`/`BE-07`/`T-UA-02`/`contract.md` §3 (D-17).
- **What's wrong:** `fds.md` REQ-PROF-04 and §6's acceptance criterion ("Confirming data deletion purges transactions, budgets, and goals while keeping the user account intact") and `behavior.md` §5's exact modal copy ("This will permanently erase all transactions, budgets, and goals. This action cannot be undone.") and success toast ("All financial records have been cleared.") all describe a destructive action against financial records. Directive D-01 (approved) scopes `clearAllUserData` in v1.0.0 to reset only `avatarUrl` and `notificationPreferences.*` to their defaults (`contract.md` §5.5) — `transactions`/`budgets`/`goals` tables don't exist yet and are never touched. `plan.md` task `FE-07` instructs Frontend Build to render "the exact warning copy from `behavior.md` §5" and the exact success toast verbatim, with no addendum anywhere narrowing that text to match D-01's actual scope. Built as written, a user confirming "Clear All Data" in v1.0.0 is told specific categories of their financial data will be permanently and irreversibly erased, and sees a success toast confirming "financial records have been cleared" — when in fact nothing but their avatar and three notification checkboxes reset to default. `T-UA-07`'s own test description ("does not modify `users.name`/`.email`/`.passwordHash`") doesn't even assert the absence of transaction/budget/goal data, because there's no such data to assert against.
- **Severity condition:** (a) Spec violation — built as written, the feature behaves differently from `fds.md` §3/§6 and `behavior.md` §5 (a stated acceptance criterion is not satisfied by its implementing task), and the discrepancy is user-facing on a high-severity destructive-action confirmation, which is precisely the kind of thing checklist point 6 ("Ambiguity carried forward") exists to catch before Build, not after.
- **Concrete failure:** The UI/E2E Test agent (Phase 8, `T-UI-12`) and the Unit/API Test agent (`T-UA-07`) would be asked to verify copy and behavior that visibly contradict each other once a reviewer compares the rendered modal text to the actual side effects — exactly the "discovered mid-Build/Test, forces a full restart from Plan Mode" scenario this checklist flags. Left uncorrected, a developer or end user will treat this as a trust-damaging bug (a destructive-action dialog that misrepresents its own blast radius), not a cosmetic one.

### B-2 — "Export Data" is documented and labeled as a financial-history export but contains none (REQ-PROF-03)

- **Origin:** Pre-existing (same basis as B-1 — not touched by either revision round).
- **What's wrong:** `fds.md` REQ-PROF-03 ("Packages all user data (transactions, budgets, goals, profile configuration) into a downloadable bundle") and §6's acceptance criterion ("downloading an archive containing user financial history") both describe an export that includes financial records. Directive D-01 (approved) scopes `exportUserData` to the `UserProfile` field set only (`contract.md` §2.6, explicit: "no `transactions`, `budgets` or `goals` keys in v1.0.0"). `T-UA-06` even asserts the field list "contains... no `transactions`/`budgets`/`goals` keys" as a passing test — directly the opposite of what the acceptance criterion describes. No addendum narrows REQ-PROF-03 or the §6 bullet to profile-only data, unlike the addendum D-16 added for `behavior.md` §1's nav-header gap.
- **Severity condition:** (a) Spec violation — same clause as B-1: an acceptance criterion with an implementing task whose approved behavior doesn't satisfy it, and whose only verifying test asserts the opposite of the AC's literal text.
- **Concrete failure:** Same mid-Build/Test discovery risk as B-1. A Validation Mode pass (Phase 9) run strictly against `fds.md` §6 as currently written would have to mark this acceptance criterion failed, even though the implementation matches the approved (but un-addended) D-01 scope.

**Both B-1 and B-2 share one root cause and very likely one fix:** D-01 changed what `exportUserData`/`clearAllUserData` actually do, but — unlike D-16, which paired its scope decision with a `behavior.md` addendum — nothing updated the FDS requirement text, the §6 acceptance criteria, or `behavior.md`'s literal UI copy to match. See Suggested Next Step.

## Advisory Findings

- **`T-UA-07`'s service-layer claim doesn't match `BE-08`'s signature.** `T-UA-07` says `ProfileService.clearAllUserData` "rejects any `confirmation` other than `DELETE`," but `BE-08` declares the method as `clearAllUserData(userId): void` — no `confirmation` parameter. The confirmation check is a request-validation concern (`ClearDataConfirmation`, `contract.md` §4, enforced by the router via the typed contract) and is already correctly tested at that layer by `T-UA-09`. The Unit/API Test agent owns both `profile-service.test.ts` and the route-level test in the same session, so it can drop or relocate the redundant line without crossing a boundary or facing an observably different outcome — not Blocking.
- **The mechanics of turning `exportUserData`'s JSON+`Content-Disposition` response into a browser-triggered file download through the ts-rest client aren't specified.** `FE-07`/`FE-08` say "browser download of the response" without saying whether this is a Blob constructed from the parsed body and an anchor-tag `download` trigger, or something else. This is ordinary implementation detail Frontend Build can resolve inside its own scope.
- **Lazy profile creation (D-11) has no documented concurrent-request handling.** `user_profiles.user_id` is `UNIQUE` (`BE-01`); two near-simultaneous first-access requests for the same user could both reach `ProfileRepository.create` and one would hit a constraint violation. `BE-05`/`BE-06` don't say whether this is caught and retried as a read. Low-likelihood edge case, resolvable inside Backend Build's own scope.
- **`preferredCurrency`/`language` enum→display-string mapping is only given for the default value.** `fds.md` REQ-PROF-02 shows one example each (`NPR (₹)`, `English (EN)`); the other three currency symbols and three language labels aren't specified anywhere. Not reachable in v1.0.0 — both fields are read-only and D-05 makes them permanently un-settable to anything but their defaults via the API — but worth settling in `fds.md` before v1.1.0 makes them editable.
