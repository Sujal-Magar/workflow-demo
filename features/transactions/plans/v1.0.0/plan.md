# Implementation Plan: transactions (v1.0.0)

- **Feature:** `transactions`, Transactions Management
- **FDS version:** 1.0.0 (`features/transactions/fds.md`, changelog entry 1.0.0 dated 2026-09-22, addended to close the `timeframe` filter as a labelled-preset enum)
- **Scenario:** New Standalone Feature. `fds.md`'s changelog has a single entry, so this plan covers the whole FDS. `features/index.json` lists `transactions` as depending on both `auth` and `profile`, but per the backend fragment (§1) and this synthesis (`contract.md` header), no backend coupling to `profile` exists at all — the only `profile` dependency is the frontend reusing the signed-in user's `preferredCurrency` via the already-built `useProfile()` hook, plus one small additive relocation of `profile`'s private `CURRENCY_SYMBOLS` constant into a shared module (D-04 below). Neither touches `profile`'s business logic, data model, or API contract. This does **not** meet the Cross-Feature Dependency scenario's bar for a 2-phase Foundation-Refactoring plan (`rules/workflow.md` §2 Phase 1) — the same reasoning `profile`'s own plan used for its lighter touch on `auth`.
- **Complexity:** spec stability 1 (one ambiguity round already resolved via an `fds.md` addendum before fragments were finalized, plus the `timeframe`-staleness conflict resolved during this synthesis — `contract.md` §7 C1) + UI/API surface 2 (multi-component page, new API contract) + team/agent separation 2 (dedicated frontend + backend fragments) = **5**, so the full Multi-Agent pipeline applies (`rules/workflow.md` §5).
- **Coverage target:** 90% (`fds.md` frontmatter — higher than `profile`'s 85%). `compliance_relevant: false`, so the Validation Report is not persistent.
- **Sources synthesized:** `fragments/frontend.md`, `fragments/backend.md`, `fds.md` (incl. the `timeframe` addendum), `behavior.md`, `visuals/*.png`, `rules/*`, `features/index.json`, and the already-frozen `features/auth/plans/v1.0.0/plan.md`/`contract.md` and `features/profile/plans/v1.0.0/plan.md`/`contract.md` for the ports, repositories, and conventions `transactions` reuses. No `directives.md` exists for this version (first synthesis run); none of the fragments required a developer decision before this run — both fragments completed cleanly as of `activity-log.md`'s last two entries.
- **API Contract:** [`contract.md`](contract.md) in this directory. It is the only definition of routes, bodies, statuses and error codes. This plan refers to it and does not repeat it.

**How to read task entries.** Each task has an ID, a `layer` (which build session owns it), the files it creates or changes, what "done" means, and its spec trace. Paths are relative to the repository root. Build agents implement tasks in ID order within their layer unless a task says otherwise.

## 3. Backend Section (`layer: backend`, paths `backend/` and `packages/contracts/`)

Layering follows `rules/architecture.md`: Presentation (router) calls `TransactionService` only; the service holds every business rule and never sees `req`/`res`; the repository is the only code that touches Drizzle. `TransactionService` is constructed with `transactionRepository: TransactionRepository`, `clock: Clock` (existing port, reused) — no new ports needed (D-10).

**Named constants** (one module, `backend/src/features/transactions/transaction-constants.ts`): `DEFAULT_PAGE = 1`, `DEFAULT_LIMIT = 10`, `MAX_LIMIT = 100` (D-08).

### BE-01 · Data model / Drizzle schema

- **Files:** `backend/src/db/schema/transactions.ts` (new), `backend/src/db/schema/index.ts` (add `export * from "./transactions"`).
- `transactions` table: `id` (text PK, UUID generated in code), `user_id` (text NOT NULL, FK → `users.id`, cascade delete, same pattern as `user_profiles.user_id`), `date` (text, `YYYY-MM-DD`), `description` (text, 1–255 chars enforced at Contract/Zod), `category` (text enum, 10 values from `contract.md` §2.4), `type` (text enum `"income"`/`"expense"`), `amount` (real, hand-added `CHECK (amount > 0)` on the generated migration, same pattern as `user_profiles_monthly_start_date_check`), `created_at`, `updated_at` (text ISO timestamps).
- Indexes: `transactions_user_id_idx` on `user_id`; `transactions_user_id_date_idx` on `(user_id, date)`.
- Migration: `backend/src/db/migrations/0002_init_transactions.sql`, next sequential index after `0000_init_auth` / `0001_init_profile` (confirmed current state).
- **Done when:** the generated migration applies cleanly to a fresh `:memory:` database and to the existing `data/app.db` schema. Tests: T-UA-01.
- **Trace:** `fds.md` §2; `contract.md` §2.1; `rules/architecture.md` Database.

### BE-04 · Repository layer

- **Files:** `backend/src/features/transactions/transaction-repository.ts`.
- `findById(id, userId): TransactionRecord | null` — scoped by both id and owner (D-02).
- `findManyByUserId(userId, filter: TransactionFilter): TransactionRecord[]` — `TransactionFilter = { category?, type?, dateFrom?, dateTo?, sort }`, an already-resolved date window (not the raw `timeframe` string — resolving it is a Service-layer concern, `rules/architecture.md` Repository Layer). Applies `category`/`type`/date-window predicates, then `ORDER BY date <asc|desc>, created_at <asc|desc>` (D-07 tie-break), then `LIMIT`/`OFFSET`.
- `countByUserId(userId, filter): number` — same predicate, no pagination, for `total` (`contract.md` §2.3).
- `create(newTransaction): TransactionRecord`.
- `update(id, userId, patch, updatedAt): TransactionRecord | null` — `null` if the scoped row doesn't exist (caller maps to `TransactionNotFoundError`).
- `deleteById(id, userId): boolean` — whether a row was actually deleted.
- No business rules in this file (`rules/architecture.md` Repository Layer).
- **Done when:** every method above exists and is covered. Tests: T-UA-01, T-UA-02.
- **Trace:** `fds.md` §5; `rules/architecture.md` Repository Layer; D-02, D-07.

### BE-05 · Service layer

- **Files:** `backend/src/features/transactions/transaction-service.ts`.
- **`listTransactions(userId, query): { data: Transaction[]; total: number }`:** resolves `timeframe` to a concrete `[dateFrom, dateTo)` window using `clock.now()` — `"this_week"` → the ISO-8601 Monday-start week containing today (D-06); `"this_month"` → first through last calendar day of the current month; `"this_year"` → Jan 1–Dec 31 of the current year; `"all_time"` → no date predicate. Calls `transactionRepository.findManyByUserId` and `.countByUserId` with the same resolved filter so `total` always matches `data`'s filter. Applies `DEFAULT_PAGE`/`DEFAULT_LIMIT` (BE constants, D-08) when `page`/`limit` are absent.
- **`createTransaction(userId, input): Transaction`:** validated at the Contract/Zod boundary (BE-02) before reaching this method; `transactionRepository.create({ id: randomUUID(), userId, ...input, createdAt: now, updatedAt: now })`.
- **`updateTransaction(userId, id, input): Transaction`:** full field set (D-01); `transactionRepository.update(id, userId, input, now)`; `null` → throw `TransactionNotFoundError` (D-02, BE-03).
- **`deleteTransaction(userId, id): void`:** `transactionRepository.deleteById(id, userId)`; `false` → throw `TransactionNotFoundError`.
- **Done when:** all four methods behave per `contract.md` §5. Tests: T-UA-02, T-UA-03, T-UA-04.
- **Trace:** REQ-TXN-01…04; `contract.md` §5; D-01, D-02, D-06, D-07, D-08.

### BE-06 · Transactions router

- **Files:** `backend/src/features/transactions/transaction-router.ts`.
- Implements the four operations from `transactionsContract` (BE-02) using the ts-rest Express adapter. All four require `requireAuth`/`getAuthenticatedUserId` (reused unchanged from `backend/src/features/auth/require-auth.ts`, same wiring as `profile-router.ts`).
- Handlers stay thin: read query/body/`:id`, call the service, return the declared status. No business logic here (`rules/architecture.md` Presentation Layer).
- **Done when:** `pnpm typecheck` passes and every route matches `contract.md` §5 exactly. Tests: T-UA-06.
- **Trace:** `contract.md` §5, §6; `rules/architecture.md` Presentation Layer.

### BE-07 · App wiring

- **Files:** `backend/src/app.ts` only. `backend/src/index.ts` needs no changes.
- Inside `createApp()`, construct `TransactionRepository` (BE-04) and `TransactionService` (BE-05) alongside `auth`'s and `profile`'s existing wiring, reusing the same `clock` instance already constructed there (not a second instance) — identical pattern to how `ProfilePersistence`/`ProfileService` were wired in (`profile` plan BE-10).
- Mount the transactions router (BE-06) inside `createApp()`, carrying its own full `/api/v1/transactions/...` path from the typed contract. Makes the router reachable from `backend/src/test-support/auth-test-harness.ts`'s `startTestApp()`.
- Update the existing `CORS_ALLOWED_METHODS` constant to include `"PUT"` (currently `"GET, POST, PATCH, DELETE, OPTIONS"`): `updateTransaction` is the first operation in this codebase to require `PUT` (`contract.md` §5.3/§6, REQ-TXN-02, `behavior.md` §3), and `createCorsMiddleware` applies this constant globally to every route, not per-router, so the frontend's (`localhost:3000`) cross-origin `PUT /api/v1/transactions/:id` preflight against the backend (`localhost:4000`) is blocked unless `PUT` is present.
- **Done when:** `pnpm dev` in `backend/` starts, `/health` still answers, `startTestApp()` exposes the transactions routes, `CORS_ALLOWED_METHODS` includes `"PUT"`, and `pnpm lint` + `pnpm typecheck` pass.
- **Trace:** `rules/architecture.md` Presentation Layer; `contract.md` §1, §5.3, §6; `profile` plan BE-10 (precedent).
