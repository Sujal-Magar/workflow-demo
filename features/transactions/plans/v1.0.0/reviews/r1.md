## Blocking Findings

### B-1 — `updateTransaction`'s `PUT` method is unreachable from the real frontend: the shared CORS middleware never allows it, and no plan task adds it

- **Plan section:** `plan.md` BE-07 ("App wiring"), and by extension BE-06 and `contract.md` §5.3/§6 (`PUT /api/v1/transactions/:id`).
- **Conflicts with:** `fds.md` REQ-TXN-02 (Edit Transaction Modal) and `behavior.md` §3 (Edit Transaction Workflow) — "On successful update, persists changes, updates the table row, and displays a success notification."
- **Concrete failure:** `backend/src/app.ts`'s `createCorsMiddleware` hardcodes `CORS_ALLOWED_METHODS = "GET, POST, PATCH, DELETE, OPTIONS"` — there is no `PUT` in the list, and this middleware is applied globally (`app.use(createCorsMiddleware(...))`), not per-router. Frontend (`http://localhost:3000`) and backend (`http://localhost:4000`) are genuinely different origins (`backend/src/config/env.ts` `DEFAULT_FRONTEND_ORIGIN`/`DEFAULT_PORT`; `playwright.config.ts`'s two `webServer` entries). `auth` and `profile` never needed `PUT` — `profile`'s own update operation uses `PATCH` (`profile-router.ts`), which is why this gap has never surfaced before. `transactions` is the first feature in this codebase to need `PUT`, and `contract.md` §5.3/§6 correctly specifies it (matching D-01's full-replace semantics) — but BE-07's "Files: `backend/src/app.ts` only" task description and its "Done when" criteria (`pnpm dev` starts, `/health` answers, routes reachable from `startTestApp()`, lint/typecheck pass) never mention updating `CORS_ALLOWED_METHODS`. A real browser's CORS preflight for the `PUT` request will see `PUT` absent from `Access-Control-Allow-Methods` and block the actual request — Edit Transaction will fail for every user hitting the real, integrated app, with no error surfaced anywhere lint/typecheck/SonarQube/Unit-API-tests would catch (`backend/src/test-support/auth-test-harness.ts`'s `startTestApp()` calls `createApp()` in-process and never goes through browser CORS enforcement, so T-UA-06 passes regardless).
- **Severity condition:** **(a) Spec violation** — built exactly as the plan and frozen contract specify, REQ-TXN-02/`behavior.md` §3 would not work through the real frontend. Also **(d) Gate cannot pass** — Phase 8 UI/E2E's `e2e/transactions-edit.spec.ts` (T-UI-10) runs against the real two-origin `webServer` setup (`playwright.config.ts`) and would fail the moment it submits the Edit form, and that failure is outside the UI/E2E Test agent's own scope to fix (`test-build-mode.md` UI/E2E Defect Handling: "only within frontend files" — `app.ts` is a backend file), forcing an escalation to Diagnosis Mode that Plan Review exists to prevent.
- **Fix is an Obvious fix**, not a developer decision: the contract already mandates `PUT`, so the one correct change is adding `"PUT"` to `CORS_ALLOWED_METHODS` in `backend/src/app.ts` as part of BE-07 (or a dedicated line item under it).

## Advisory Findings

- **BE-04 parameter naming**: `update(id, userId, patch, updatedAt)` names its fourth parameter `patch`, even though D-01 and `contract.md` §2.5 are explicit that `updateTransaction` is a full field replace, not a partial patch. Purely a naming choice inside Backend Build's own task; does not change any declared behavior.
- **`amount` column type**: BE-01 stores `amount` as a Drizzle `real` (floating-point) column. Neither `fds.md` nor `rules/` specifies a storage representation for currency amounts, so this is not a plan/spec conflict, but it's worth the developer's awareness given `amount` is money — same risk profile as any floating-point currency field, not introduced or worsened by this plan beyond the general pattern.
- **FE-06 Date field placeholder** and **FE-04 category glyph choice** are both explicitly left to Build Mode's visual judgment with a documented rationale; both are Phase 6 UI Review's job to confirm against `visuals/transaction-add-modal.png`/`transactions-page.png`, as the plan itself notes.
