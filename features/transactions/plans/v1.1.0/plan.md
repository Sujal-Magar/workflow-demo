# Implementation Plan: transactions (v1.1.0)

- **Feature:** `transactions`, Transactions Management
- **FDS version:** 1.1.0 (`features/transactions/fds.md`, changelog entry 1.1.0 dated 2026-10-04, including the clarification that fixed the `title` backfill formula and the UTC basis of the server-set `date`)
- **Scenario:** Existing Feature Update. Scope is the 1.1.0 changelog entry only: (1) a required `title` field, 1–100 characters; (2) the Add/Edit modals' first control becomes a Title text input and the date picker is removed; (3) `date` is set by the server to the UTC creation date and never changes on update; (4) the ledger gains a Title column; (5) existing records backfill `title = SUBSTR(description, 1, 100)`. Everything else in the FDS was planned and built under v1.0.0 (`../v1.0.0/plan.md`, built through Integration per `activity-log.md`) and is carried forward unchanged. It appears here only as regression tests the change may affect. This is not a Cross-Feature Dependency plan: no `auth` or `profile` file changes.
- **Baseline:** the code on `feat/transactions` at commit `1c226d9` ("integration build complete"). v1.0.0 Phase 7b, 8, 8c and 9 never ran: there are no `transactions` test files in `backend/`, `packages/contracts/`, `frontend/` or `e2e/`. See D-26 for how this plan handles that.
- **Complexity:** spec stability 1 (two FDS clarification rounds were needed for 1.1.0, now closed) + UI/API surface 1 (changes to existing components and an existing API) + team/agent separation 2 (separate frontend and backend fragments) = **4**. The full Multi-Agent pipeline applies (`rules/workflow.md` §5). Build runs one layer at a time, in a fixed order, for the reason in D-15.
- **Coverage target:** 90% (`fds.md` frontmatter), applied at Phase 8c. `compliance_relevant: false`, so the Validation Report is not persistent.
- **Sources synthesized:** `fragments/frontend.md`, `fragments/backend.md`, `fds.md` 1.1.0, `behavior.md`, `visuals/*.png`, `rules/*`, `features/index.json`, the frozen `../v1.0.0/plan.md` and `../v1.0.0/contract.md`, and the built code where a fragment's claim affected a decision (D-15, D-21, D-27). No `directives.md` exists for this version (first synthesis run).
- **API Contract:** [`contract.md`](contract.md) in this directory. It is the only definition of routes, bodies, statuses, rule sets and error codes. This plan refers to it and does not repeat it.

**How to read task entries.** Each task has an ID, a layer (which build session owns it), the files it changes, what "done" means, and its spec trace. Paths are relative to the repository root. Build task IDs continue the v1.0.0 numbering (BE-08 onward, FE-10 onward, INT-05 onward) because the built code already cites v1.0.0's BE-01…BE-07, FE-01…FE-09 and INT-01…INT-04 in its comments; reusing those IDs would make those comments ambiguous. Test IDs restart at T-UA-01 / T-UI-01 and replace v1.0.0's test list, which was never executed (D-26).

## 3. Backend Section (`layer: backend`, paths `backend/` and `packages/contracts/`)

Layering is unchanged (`rules/architecture.md`): the router calls `TransactionService` only, the service holds every business rule and never sees `req`/`res`, and the repository is the only code that touches Drizzle. `TransactionService` keeps its two dependencies, `transactionRepository` and `clock`. No new error codes or `DomainError` subclasses (D-09): `error-handler.ts` and `validation-error.ts` need no edit. `transaction-router.ts` needs no edit: its handlers pass `body` to the service, and the new field set reaches them through the contract's request schemas.

### BE-08 · Contract package: `title` in, `date` out of the requests

- **Files:** `packages/contracts/src/transactions/transaction-shapes.ts`, `packages/contracts/src/transactions/transaction-validation.ts`.
- `transactionSchema`: add `title: string` (no length bound on the response shape, `contract.md` §2.1, D-21).
- `transaction-validation.ts`:
  - Add `TITLE_MAX_LENGTH = 100` and messages `TITLE_REQUIRED: "Title is required."`, `TITLE_TOO_LONG: "Title must be at most 100 characters."` (`contract.md` §4, D-19).
  - Add `transactionTitleSchema`, written in the same style as `transactionDescriptionSchema` (trim, then the two checks, returning the trimmed text).
  - `createTransactionRequestSchema` becomes `{ title, description, category, type, amount }`. `updateTransactionRequestSchema` stays an alias of it (D-01). Both stay plain objects that strip unknown keys, so a sent `date` is dropped (D-17).
  - Remove `transactionDateSchema`, `isValidCalendarDate`, `DATE_PATTERN`, `DATE_REQUIRED`, `DATE_INVALID` (D-24).
- **Done when:** the package exports `transactionTitleSchema` and the updated schemas and types; nothing in it references a date rule; `pnpm --filter @workflow-demo/contracts --filter backend typecheck` passes once BE-10 and BE-11 are also done. The two frontend errors named in D-15 are expected here and are fixed by FE-11.
- **Trace:** `fds.md` §2, §5; `contract.md` §2.1, §2.5, §4, §8; D-01, D-17, D-19, D-24.

### BE-09 · Drizzle schema and migration `0003`

- **Files:** `backend/src/db/schema/transactions.ts`; `backend/src/db/migrations/0003_<generated-name>.sql` (new); `backend/src/db/migrations/meta/0003_snapshot.json` and `meta/_journal.json` (generated).
- Schema: add `title: text("title").notNull()` after `userId`. Update the file's header comment to say `date` is set by the server, in UTC, at creation.
- Generate with the existing `pnpm --filter backend db:generate`, so the snapshot and journal entry come from the tool. Then rewrite the SQL body by hand to the table rebuild in D-20, in this order, separated by `--> statement-breakpoint` as the existing migrations are:
  1. `CREATE TABLE __new_transactions (…)` with every v1.1.0 column, the `user_id` FK `ON DELETE cascade`, and `CONSTRAINT transactions_amount_check CHECK (amount > 0)`;
  2. `INSERT INTO __new_transactions (id, user_id, title, date, description, category, type, amount, created_at, updated_at) SELECT id, user_id, SUBSTR(description, 1, 100), date, description, category, type, amount, created_at, updated_at FROM transactions;`
  3. `DROP TABLE transactions;`
  4. `ALTER TABLE __new_transactions RENAME TO transactions;`
  5. recreate `transactions_user_id_idx` and `transactions_user_id_date_idx`.
- No `PRAGMA foreign_keys` toggling: no table references `transactions`.
- **Done when:** the migrations apply cleanly to a fresh in-memory database and to a database already at `0002` that contains transactions (verified hands-on in INT-05, tested in T-UA-01); the generated snapshot matches the Drizzle schema.
- **Trace:** `fds.md` §2 (`title` row and its backfill rule); D-20.

### BE-10 · Repository: `title`, no `date` on update, `id` tie-break

- **Files:** `backend/src/features/transactions/transaction-repository.ts`.
- `TransactionRecord` and `NewTransaction`: add `readonly title: string`. `NewTransaction` keeps `date` (the service supplies it).

- `toTransactionRecord` maps `row.title`; `create` writes it.
- `findManyByUserId`: order by `date`, `createdAt`, then `id`, all in the requested direction (D-22).
- No new methods. `findById`, `countByUserId`, `deleteById` and the filter predicate are unchanged.
- **Done when:** the types above compile, and the repository persists and returns `title`, cannot write `date` on update, and orders with the `id` key. Tests: T-UA-02.
- **Trace:** `fds.md` §2; `contract.md` §2.3; D-07, D-18, D-22.

### BE-11 · Service: server-set UTC `date`, `title` mapping

- **Files:** `backend/src/features/transactions/transaction-service.ts`.

- `createTransaction(userId, input)`: `input` is `{ title, description, category, type, amount }`. Take `now = clock.now()` once; pass `date: formatDate(now)` and `createdAt: now` (D-16). Reuse the existing `formatDate`; do not add a second date helper.
